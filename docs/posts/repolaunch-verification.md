# 三个仓库跑通之后，验证结论该怎么写

**记录阶段**：2026 年 10 月下旬 · 10 月 28 日整理

一次演示最容易展示的是“页面打开了”。但写技术复盘时，我还需要回答：测的是哪份源码、检查了什么、哪些步骤使用替身，以及失败样例有没有被省略。

## HTTP 200 回答的问题很有限

执行器先启动容器，再检查方案指定路径的 HTTP 响应。拿到 2xx，说明检查时该路径可以正常响应。

它不能证明登录、数据库读写或整条业务流程都正确。某个项目即使只返回默认欢迎页，也可能通过这个层级的检查。

因此真实仓库验收额外加入内容探针。例如 FastAPI 样例除了检查根路径，还访问 `/items/7?q=test`，核对返回 JSON 中预期字段。

## 保留的三个样例

以下是 2026 年 10 月 26 日文档中记录的样例结果；不是本篇整理时重新测出的新一轮数据。

| 仓库 | 固定提交简写 | 总耗时 | 规划请求 Token |
| --- | --- | ---: | ---: |
| render-examples/flask-hello-world | `facfc73` | 28.02 秒 | 985 |
| digitalocean/sample-flask | `3f22698` | 35.3 秒 | 3538 |
| render-examples/fastapi | `f829276` | 148.77 秒 | 1849 |

总耗时包含仓库读取、规划和构建等步骤，受网络、缓存和依赖下载影响。Token 列只统计对应规划请求；嵌入、修复与其他请求不能悄悄并入这个数值解释。

这三个仓库经过选择，规模和环境较简单。三个通过只能证明这三个具体样例通过，不能写成“开源项目部署成功率 100%”。

## 自动化测试与外部联调要分开

项目记录了 233 项自动化测试和 29 个子测试通过；另有一项需要主动开启的 Docker 测试，在工具环境中跳过。这个跳过结果与普通 Windows 会话下完成的真实 Docker 验收，是两份不同证据。

使用替身的测试适合检查命令参数、权限限制、取消和异常分支。真实联调才能回答 Docker 引擎、模型服务、MySQL、Milvus 和 Langfuse 是否在当时环境下实际工作。

GitHub Actions 是否通过也应该查看对应提交的运行结果，不能把本地测试结果直接当成远程 CI 结果。

## 失败样例同样进入结论

已有目标仓库出现 setuptools 平铺目录包发现错误，当前窄补丁不能修改它的打包声明。这次失败保留在支持边界中，不计入上面的三个通过样例。

在记录下一轮验证时，我会优先补充失败类别与覆盖范围，再考虑增加一个总分。否则分数增长可能只是因为挑选了更容易运行的仓库。

## 给下一轮验证留下什么

每项至少保存目标仓库与完整提交、运行环境、方案、构建日志、HTTP 检查、内容探针、耗时和失败原因。模型用量单独记，测不到的字段保持未知。

这些字段能帮助下一次区分：是代码变了、环境变了、模型建议变了，还是同一故障再次出现。
