# 学习笔记 06｜意图识别与对话管理：让系统听懂「这个能退吗」

**日期**：2026-07-06
**标签**：AI Agent · 意图识别 · 对话管理

> 上一章画图时「意图识别」站只挂了一块施工警示牌。这一章把它做实，顺便把两个前文留的坑一起填上：RAG 章留下的「检索前怎么拆查询」，以及「它」「这个」这类指代该怎么补全。一句话的完整旅程从这章起变成：**先补全指代 → 改写归一 → 扩写多查 → 判意图 → 送上五条轨道之一**。

## 一、指代消解：先把「这个」补成一句完整的话

用户冒出一句「这个能退吗」，系统要同时想明白两件事：「这个」指哪件商品？「能退吗」是想问政策、铁了心要退、还是投诉？前者判断错了，检索就找错知识条目；后者判断错了，流程走岔。

「这个」藏在上一轮对话里（前一句刚问过「蓝牙耳机什么时候到货」）。把这类依赖上下文才能看懂的话，改写成一句脱离历史也看得懂的完整问句——这就是**指代消解**。做法：拿本轮新消息 + 最近几轮历史，交给 LLM 输出一句语义完整的改写：「这个能退吗」→「蓝牙耳机还能申请退货吗」。往后不管是检索还是判意图，用的都是这句改写，不再是半截话。

**边界**：问题本身已经完整明确（「蓝牙耳机的保修期是多久」），就该原样透传，不强行改写——硬凑可能引入历史里不存在的信息，越改越偏。

## 二、Query 改写与扩写：求准与求全，两条不同的路

### 改写求准（指代消解是它的一种手法）

把口语化、含糊的问法归一成贴近知识库表达的标准问法。一句话变一句话。

### 扩写求全

检索只拿「蓝牙耳机还能申请退货吗」一句去查，知识库里写的可能是「无理由退换货规则」，字面依然对不太上。让模型泛化出几条侧重点不同的查询一起查，再去重合并：

```text
## 角色
你是电商客服的查询优化助手，把用户问题泛化成多条检索友好的中文查询，用于知识库检索。

## 改写规则
1. 出现产品名、型号、平台这类关键实体时，改写要保持一致。
2. 不要引入原问题里没有的型号、参数、数值。
3. 每条查询尽量短、含关键词，彼此侧重点不同。

## 输出要求
严格 3 条，必须使用以下 JSON 格式返回，不得包含任何其他文本：
{"queries": ["蓝牙耳机退货政策", "蓝牙耳机无理由退换货条件", "耳机退货时间限制"]}
```

### 扩写不是白拿的

查询条数翻倍，检索和精排耗时跟着翻倍。**只对核心业务场景做**——退款退货、售后这类高频、容错低、措辞容易不一的问题；「客服电话是多少」这种简单 FAQ 原始问题直接查就够了。

**扩召回放检索侧现查现用，绝不放入库侧**（填上一章留的坑）：如果一条知识预先泛化成多种问法、每种配一份答案存库，一个用户问题进来，这几份几乎一样的内容同时冲进 Top-K，占掉该留给其他知识的名额。库里知识只留一份，查询时才临时生成变体，用完即扔。

## 三、意图体系不是一次画出来的

刚上线的客服系统往往只分得出「产品咨询」「闲聊」两类，够应付大部分场景。上线一段时间翻真实对话才发现：用户还会主动提建议、报故障，两类处理逻辑完全不同（故障要记录等级上报、建议要落库复盘）。类目表跟着真实流量被撑大。

电商场景同理：物流、订单、商品咨询第一天就看得出来；退款退货和普通售后一开始很容易归成一类，直到发现处理路径完全不同——退款退货走审核流程，普通售后可能就是答一句保修条款——才拆成两个意图。

**看数据说话，而不是先验地画一张完美类目表。**

最终本项目九类：物流、订单、商品咨询、退款退货、售后、投诉、人工、闲聊、其他。

## 四、三条技术路线：关键词 → BERT → LLM Prompt

| 路线 | 优点 | 卡点 |
|---|---|---|
| 关键词匹配 | 实现最快 | 换个说法就失灵（「多久能到」vs「什么时候发货」），表达穷举不完 |
| 微调 BERT 分类器 | 准、快、省、部署成本低 | **意图漂移**：用户问物流，聊两句切到退款，又绕回物流。判断当前步归哪类，得读懂整段对话推进的脉络，孤立看一句话下不了结论。BERT 单句分类没法处理，除非把整段历史塞进分类器重新设计输入——工作量超出微调能兜住的范畴 |
| **LLM Prompt** | 零样本、能读整段历史 | —— |

**往深一层**：这不只是「挑一个类别」，业内更准的叫法是「对话状态追踪」——每一轮过后，对话处于什么状态、用户诉求解决没有、这句话把状态往哪推了一步，都要更新。意图识别只是这层状态追踪露出的一个切面，「对话管理」四个字指的就是这个。

## 五、模型怎么配：先求准，再求省

- 多轮客服默认配**能力够格的大模型**判意图，不必为省钱先挑小模型——判错一次后面整条路跑偏，影响面比省点钱大得多
- 成本吃紧时走降级路：**小模型先判 + 置信度**，置信度够高直接采用，只有低置信度的小撮问题升级大模型重判——把大模型调用量压在真正需要它的地方
- 选型不是定终身：初期先上大模型把准确率做上去，跑稳、基线摸清后，再在不降准确率前提下把日常流量换成 Qwen-plus、GLM 免费 Flash 档这类更便宜的模型

---

## 六、Prompt 四件套：把判断题改造成选择题

模型选好了，判得准不准还有一半功夫在 Prompt：

1. **枚举做选择题**：候选意图列成表让模型选，不是开放回答——开放提问模型今天答「用户想问退货」，明天换个说法，下游代码没法稳定解析
2. **强制 JSON**：`{"intent": "...", "confidence": 0.0-1.0}`，不许夹带解释性文字
3. **few-shot 补边界**：光讲规则模型照样在拿不准的地方猜，补一两个边界样例（「用户说『这个还能退吗』，意图是退款退货，不是商品咨询」）比大段文字描述管用
4. **留兜底类**：「其他」专门收判断不了、又不该硬塞进某个业务意图的问题——宁可归兜底，别硬贴标签

**边界定义和模型能力一样重要、谁也替代不了谁**：复杂场景模型能力不够，抠措辞压不住；模型够格但类目边界写不清楚，输出照样飘。比如「人工」和「投诉」的边界：只是发泄不满、要个说法归投诉；明确说建工单、转人工，哪怕问题还没讲清楚也归人工。

---

## 七、意图一多，Prompt 塞不下（面试延伸）

大型客服系统动辄三五百个细分意图，全塞一段 Prompt 又长又贵，选项一多模型挑花眼。两套成熟解法：

1. **两级分类**：先粗分少数大类（物流类/售后类/其他），命中大类再进内部细分。代价是维护一棵两层意图树，换来每级简短
2. **检索式意图识别**：把每个意图描述当一篇文档建向量库，用户问题先向量检索召回十来候选，再让模型只在候选里挑——意图再多，塞进 Prompt 的候选数恒定。思路挪的是前面 RAG 两章的能力

---

## 八、缺的信息谁来问：不在意图识别这一站

信息不够（退款要订单号、退款原因）该在哪问？**都不在意图识别站，是判完意图、走到执行阶段才补齐的事。**

- 订单号：交给主力 Agent，执行循环里缺了就弹订单选择器，用户从自己订单里点一单回填
- 退款原因：不开口问，用户提交退款申请时从固定类目下拉框自选

**硬性规矩：系统缺信息不能瞎猜、不能编答案糊弄，该问就问。** 职责边界：意图识别只回答「用户想干嘛」，追问缺的槽位是执行阶段跑起来才知道缺什么的事。两件不相干的事混在一起，谁的职责都说不清楚。

## 九、分流：九类意图 → 五条出口

```python
def route_by_intent(state: ConversationState) -> str:
    intent = state["intent"]
    if intent == "投诉":
        return "escalate"
    if intent in ("闲聊", "其他"):
        return "fallback_script"
    if intent == "商品咨询":
        return "knowledge"
    if intent in ("退款退货", "售后"):
        return "refund_flow"      # 确定性子流程：取单、检索政策、只判能不能退
    return "business"             # 物流、订单、人工：直接交主力 Agent
```

| 出口 | 走什么路 | 哪些意图进来 | 守的规矩 |
|---|---|---|---|
| `knowledge` | 强制检索 → 置信度闸 → Agent 作答 | 商品咨询 | 必须先检索，证据不够不让答 |
| `refund_flow` | 取订单 → 检索政策 → Agent 判能不能退 | 退款退货、售后 | 取证一步不能省，只把最后一个判断交给模型 |
| `business` | 主力 Agent 自己调工具 | 物流、订单、人工 | Agent 自己决定调哪个接口 |
| `fallback_script` | 固定话术，不过模型 | 闲聊、其他 | 不进 Agent，零成本 |
| `escalate` | 安抚 + 转人工 | 投诉 | 不让模型接手 |

**识别要细、处理要合**：标签分九类是给日志统计和按意图算成本用的；处理归五条路是因为走法确实只有五种。代码里这张映射表只有一份，分流和日志都读它。

## 十、代码走读要点

### 先验框架行为：smoke_interrupt.py

写代码前先写一个不调模型的冒烟脚本，钉死四件事：中断返回态结构、`Command(resume=v)` 续跑取值路径、中断出现在流式哪种 chunk、图外直接调用含 interrupt 的节点抛什么。**为什么值得单开脚本**：这四条决定后面十几个任务怎么写——中断出现在 `updates` 还是 `messages`，决定 `_stream_events` 判断写在哪分支；resume 值从哪冒出来，决定 `fetch_order` 怎么接住点选。猜错一条，返工一片。

### 指代消解

```python
async def resolve(query: str, history: str = "") -> str:
    try:
        model = get_chat_model()
        r = await (COREF_REWRITE_PROMPT | model).ainvoke(
            {"query": query, "history": history or "(无)"})
        text = (r.content if isinstance(r.content, str) else "").strip()
    except Exception:
        return query
    return text or query
```

- 没走结构化输出——要的就是一句话，`Field` 那套约束没意义
- `except` 兜底 + `text or query` 两道保险：消解是整条链第一步，挂了不能把后面带崩，回落原话
- 消解结果写 `resolved_query`，原始消息还在 `messages`——下游想要哪个取哪个，日志和落库用原话
- `_history_text` 的 `prior = msgs[:-1]` 一刀不能少：最后一条是本轮待消解的话，是处理对象，不能同时当自己的上下文，否则模型看到「那它呢」既在历史里又在问题里，容易原样返回

### fetch_order：退款子流程第一步

```python
# 4+ 位连续数字视作订单号;用 lookaround 而非 \b——CJK 与数字同属 \w,\b 在「订单1001」处不成立
_ORDER_RE = re.compile(r"(?<!\d)(\d{4,})(?!\d)")

async def fetch_order(state) -> dict:
    uid = state.get("user_id", "")
    oid = state.get("order_id") or _extract_order_id(...)
    while not business.owns_order(uid, str(oid or "")):
        orders = business.list_user_orders(uid)   # 只读,可安全重跑
        oid = interrupt({"type": "select_order", "orders": orders})
    data = business.order_snapshot(oid)
```

- **lookaround 的坑**：`\b` 是单词边界，判据是两侧一个属 `\w` 一个不属。中文汉字在 Python Unicode 模式下属 `\w`，数字也属 `\w`，所以「订单1001」里「单」和「1」之间不构成边界，`\b\d{4,}\b` 一个都匹配不到。这条注释救了不少时间
- **`while` 而不是 `if`**：resume 回来的值同样不可信，得走同一道归属校验，用户点了别人的单接着弹
- **核心纪律：`interrupt` 之前只做只读操作**。resume 时被中断节点从头重跑（不是从 interrupt 那行接着跑），前面的代码执行两遍——写库、扣款、发消息这类有副作用动作放前面会做两次。这里只有抽号和列订单，重跑安全
- **归属校验放这里的理由**：退款子流程是确定性节点，不经过 `agent_tools`，工具里那道校验够不着。用户随口报的号、resume 端点回传的号都是外部输入，都得过同一道判断

### retrieve_policy：带订单状态的扩写检索

跟知识路的 `retrieve_knowledge` 比多两件事：
1. **订单状态拼进种子问题**：同样问「能退吗」，已签收和未发货适用的条款不一样，不带状态去检索召回的政策可能压根用不上
2. **扩写三条各查一遍再合并**：退款政策散落在退货条款、运费规则、时效说明好几处，单条 query 难一次全捞到。合并按 chunk id 去重、保留每个 id 最高分——同一块被两条 query 都命中很正常，取命中最好的那次排序才合理，取最后一次或平均都会失真

`qs[:3] or [query]` 兜底跟 coref 一个思路：扩写失败也得保证至少一条能查，不能让这一步失败掐断整条退款链。

### submit_refund：语义是「交出入口」，不是「已退款」

```python
@tool
async def submit_refund(order_id=..., user_id: Annotated[str, InjectedToolArg], reason=None) -> dict:
    """判定这一单可以退款后,调用本工具发起退款申请。实际提交由前端退款表单确认后落库,
    本工具只表示『这一单可以退,已把提交入口交给用户』。"""
    if not owns_order(user_id, order_id):
        return dict(NOT_OWNED)
    return {"status": "待用户确认", "order_id": order_id}
```

- **语义必须写进 docstring**：不写的话模型调完看到 status 成功，下一句就跟用户说「已为您办理退款」，而实际上什么都没发生
- **二次确认门 ≠ 归属校验**：用户在表单点确认，确认的是「要不要退」，不能证明「这单是他的」，归属得单独校验
- **agent_tools 拦截里的后门**：`submit_refund` 在拦截分支就被拦下、根本不进执行引擎，工具函数体里的 `owns_order` 永远不执行——校验写了也是死代码，所以拦截之前必须再判一次。写两遍是有意的：工具那份保「万一哪天不拦了走了引擎」，这份保当下这条路径
- **拒绝要给出路**：用户报错订单号，光回「没找到」等于把人堵死，他不知道自己的单号是多少。把名下订单列出来让他点，一步接上
- **回灌那句「不要再调用任何工具」必须写**：ReAct 环还在转，不明确叫停，模型下一步很可能又查一次订单，或干脆再调一次 submit_refund

### interrupt 传到前端

```python
if "__interrupt__" in chunk:
    payload = chunk["__interrupt__"][0].value
    ev = {"type": "interrupt", "kind": payload.get("type", ""), "conversation_id": cid}
    for k in ("orders", "preview"):
        if payload.get(k) is not None:
            ev[k] = payload[k]
    yield ev
    return
```

- 中断发生**不发 done 帧**，所以 `conversation_id` 必须挂在中断帧上，前端拿它才知道续跑用哪个会话——这是调前端时才暴露的，正常结束路径会话号在 done 帧里
- `/api/actions/resume` 一个端点服务两种中断（订单选择器回字符串、工单预览回字典），事件流跟 `/api/chat` 六种帧完全同构，前端共用解析
- **resume 值形状守卫**：前端在工单确认场景误传了 `order_id`，decision 是字符串不是字典，一律按未确认处理——宁可让用户重来，不让节点炸
- **退款原因落库用 `Literal` 枚举**：模型可以顺手填自由文本原因，但真正落库那份必须是用户从固定类目选的——工单系统要按原因分类统计，自由文本进去就统计不动

## 十一、实战要点

功能需求七条：① 指代消解（已完整原样透传不硬改）；② Query 改写归一（与消解一并处理）；③ Query 扩写（强制 JSON 单字段，只给退款退货/售后核心场景，扩写放检索侧）；④ 意图识别 LLM prompt 四件套（枚举选择题/强制 JSON/few-shot/兜底类）；⑤ 分流精化（退款退货+售后走确定性退款子流程：取单→扩写检索政策→只把「能不能退」交 Agent）；⑥ 槽位处理（缺订单号弹选择器不猜、退款原因固定类目自选、需求澄清留在 Agent、意图识别只判要干什么）；⑦ 前端配套（订单卡片可点选回填、退款单表单下拉）。

验收四条：① 多轮对话用例（物流→退款→再聊回物流）每轮意图判对、指代补全对；② 意图 JSON 稳定可解析，怪问题落「其他」；③ 问「这个能退吗」能看到先补全指代、再走退款子流程拿订单和政策；④ 浏览器不带订单号问退款，弹出订单选择器，点选后子流程接着走完。

技术栈：无新增组件；意图识别默认配够格大模型，成本吃紧再走置信度降级路由。本章不做：微调小模型/BERT、跨会话记忆。

## 十二、本章小结

- **指代消解**：半截话补全成完整问句；已完整就不硬改
- **改写/扩写**：求准归一、求全多查；扩写成本高只给核心场景；扩召回在检索侧现查现用，库一份
- **意图体系**：跟着真实流量长，先两类后九类；识别要细、处理要合
- **路线**：关键词 → BERT（卡在多轮意图漂移）→ LLM Prompt（能读整段历史）；对话状态追踪是更高一层的视角
- **模型配法**：先求准再求省；置信度降级路由
- **Prompt 四件套**：枚举选择题、强制 JSON、few-shot、兜底类
- **interrupt**：把「停下来问用户」变成一行代码；代价是中断前只读、节点可重跑
- **职责边界**：意图识别只判「要干什么」，缺槽位在执行阶段收

下一章处理对话变长的头疼：历史全塞撑不住、全裁掉又丢掉「最开始那个订单」这种跨窗指代——三层上下文管理。
