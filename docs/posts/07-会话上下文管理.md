# 学习笔记 07｜会话上下文管理：滑窗打底 + 异步摘要

**日期**：2026-07-12
**标签**：AI Agent · 上下文管理

> 从用户开口那一刻起，有个东西一路跟着车厢往下走：指代消解要翻它才知道「这个」指哪件商品，意图识别要读它才判得出用户从物流聊到了退款，主力 Agent 的 ReAct 每走一步又往里塞一段新的思考和工具结果。这个被全程翻看、被一路塞东西的家伙，就是本章主角「会话上下文」。第 1 章的简单裁剪只是够用先跑，这一章把它升级成正经的分层上下文管理。**只管当前这一通会话，不跨会话、不攒用户画像。**

---

## 一、第 1 章那版滑窗，到底漏在哪

用户上来问「蓝牙耳机 A 什么时候能到货」，接着聊 B 款 C 款音质、颜色、下单、报订单号、问满减活动，十几轮后冷不丁来一句「我之前问的那个耳机，下单之后还能改收货地址吗」。

「那个耳机」指最开头那款 A，可滑动窗口只留最近几轮，开头那轮早被挤出窗口。指代消解一翻历史，压根找不到「那个耳机」的着落——只能追问，或按最近聊的 C 款去查，答得驴唇不对马嘴。

**病根**：滑窗那个「最近的通常最相关」假设大多数时候成立，可扛不住用户忽然回头翻旧话题。窗口只认位置、不认内容，早期那轮不管多关键，只要位置够老一律照扔。

---

## 二、该带哪些历史：三种选法

| 选法 | 做法 | 长处 | 短板 |
|---|---|---|---|
| **滑动窗口** | 取最近 N 轮 | 快、省、好实现 | 用户回头翻旧话题就没辙 |
| **语义检索** | 历史每轮向量化，当前问题当钥匙去检索，按内容捞 | 二十轮前最贴的那轮也能捞回来 | 要单独建向量索引、多算嵌入；偶尔捞回「主题像、语境不搭」的旧内容 |
| **主题重要度** | 「买来送人是关键前提，得开增值税发票」这类关键事实单独标出、单独留底 | 贯穿全程的前提不被裁 | 要一步预处理判哪些是关键事实 |

**三招合着用，各补一个窟窿**：固定带最近几轮保住时效（「就这个吧」「那款呢」实词少、语义信号弱，靠位置带最稳妥）；语义检索把远处相关的捞回来；关键事实单独留底免得被裁。

**本课量级**：先把滑窗这一种打底做扎实，另两种按需再上——设计是权衡的艺术，真的需要才上。

## 三、早期对话：是砍掉，还是压缩

- **截断**：先进先出砍最老的。零成本，但订单号、一早提过的诉求跟着一起没了，切掉再也找不回来
- **摘要压缩**：早期对话不直接扔，先请模型压成一小段梗概替换原文。省空间可观、关键信息留着；代价多一次模型调用，压不好还可能漏细节

**取舍**：对话里早期内容基本是废话，截了不心疼；可客服场景早期常埋着订单号、关键诉求，一刀切掉风险太大——摘要那点额外开销花得值。真正生产做法是两条路摆在一起用，互补。

## 四、分层落地：越近越完整，越远压得越狠

1. **最近这层管保真**：最近几轮原文一字不压。「那它呢」「就这个吧」稍微压一压语气和指代就变味，判断立刻跟着出错
2. **中间这层管过渡**：用户原话一个字不动；客服答复只留开头几十个字（头一句通常就是结论）；工具结果小的原样留、大块换成一行标识。**压掉的是我们自己说过的话，留下的是「那双跑鞋」「订单 1001」这些指代要用的线索**
3. **最远那层才压成摘要**：降级到中间层、又被挤到更前的，异步压成一小段梗概

**为什么不全原文直接跳摘要**：压摘要得调模型，中间层靠规则截一截就成，不花钱不占时间——轻的手段能扛住，就别先动用贵的。

**梗概一段段攒、压完不回头重写**：压完一批就定死，往后再压新的一批不回头动它。不把旧梗概跟新滑出对话一起重压——那样第五版摘要就是最早那批内容被有损压缩了五次的结果，订单号哪一次被模型判成不重要给丢了，事后谁也查不出来。**一个事实只经历一次压缩。**

**摘要怎么生成，必须异步**：每轮回复前同步现压一次，用户得干等模型先压缩再回答。触发后 `create_task` 后台跑，存进业务库单开的会话摘要表，下一轮直接取最近几段拼上，全程不阻塞回复。

**触发看用量、不数条数**：一轮长短不固定（「好的」是一轮，贴一段物流单也是一轮）；更要命的是工具结果压根不落消息表，数条数看不见它涨，可它恰恰最占地方。

## 五、摘要提示词：把模型摁在规矩上

```text
## 角色
你是电商客服对话的摘要助手，把下面这段较早的对话压成一条「历史摘要」，留给后续的指代消解和意图识别当线索。

## 规则
1. 只提炼事实与诉求：问过哪款商品、已报上来的订单号或手机号、明确的诉求、还没解决的问题
2. 绝不添油加醋，对话里没出现过的内容一个字都不许补
3. 寒暄、语气词、跟业务无关的闲聊一概不留
4. 控制在几十到一两百字，压得比原文还长就算失败

## 输出要求
只返回如下 JSON，不要输出任何多余文字：
{"summary": "string"}
```

「绝不添油加醋」最不能松——摘要里掺进一句对话没说过的话，等于往上下文里掺假，后面的判断全跟着错。这段梗概能让下游读出聊过哪款耳机、订单号多少、卡在哪一步，就算合格。

**梗概不必全量带**：带最近三两段就够覆盖相当长一段历史，更老的留在库里事后复盘查得到。

## 六、拼装顺序：一处顺序换来了九成六的缓存命中

```python
messages = [
    # ① system：人设、红线、工具定义，每轮都一样，前缀缓存全靠它
    {"role": "system", "content": "你是电商客服助手，……"},
    # ② 中间那层：截短过的老对话
    {"role": "user", "content": "有别的颜色吗？"},
    {"role": "assistant", "content": "这款目前有黑白两色，黑色现货，白色…（略）"},
    # ③ 最近几轮原文：一字不压
    {"role": "user", "content": "满 300 减 50 能叠运费险吗？"},
    # ④ 用户当前这句话
    {"role": "user", "content": "我之前那个耳机，下单后还能改收货地址吗？"},
    # ⑤ 本轮材料：梗概和证据合成一条，挂在用户那句之后
    {"role": "user", "content": "【历史摘要】…【检索证据】…"},
]
```

**两条硬约束（都是实测撞出来的）**：

1. **整条列表只有一条 SystemMessage，内容恒为 `AGENT_SYSTEM`，一个字的可变内容都不许拼进去**。各家的 prompt caching 按渲染后的**前缀精确匹配**，system 是 `messages[0]`，把每轮都变的检索证据拼进去，整个前缀从第一个 token 就对不上。本项目被挡在变量后面的是 system + 工具 schema 那两千来个 token，本该次次命中；ReAct 环每走一步重新拼一次，一轮对话这笔损失是乘上去的
2. **摘要不许单独占一条 system**。上游 chat template 会把列表里所有 system 上提、合并成一个头部块渲染，摘要放第二条 system 等于拼在 AGENT_SYSTEM 后面，工具 schema 又被挤到可变内容之后——摘要是每个会话各不相同的，前缀照样作废。实测：摘要一进 system，缓存命中直接归零

**插入位置也有讲究**：本轮材料落在滑窗里**最后一条用户消息之后**，为的是 ReAct 轮内也能命中——第 2 步的消息列表 `[Sys, 问, 材料, AI, Tool]` 完整包含第 1 步的 `[Sys, 问, 材料]` 作前缀。

**验证缓存生效有个坑**：拿**同一个问题**问两次测不出东西（证据相同，改之前 system 本来就一样会命中）；得拿**不同的问题**各开会话跑——两次证据完全不同，但共用前缀被完整复用 2176 个 token、占输入九成六，这才是改动换来的东西。另外各家缓存粒度不同（有的按大块记，共用前缀不满一整块就报 0），别拿单一上游的零下「没用」的结论。

## 七、每层给多少：从模型窗口倒推

几个数没有统一定数（有的轮一句「好的」，有的轮贴一段物流单），所以**别写死成常量，从模型窗口倒推**：

```
fixed = 系统提示+工具schema + 检索证据 + 注入摘要 + 输出预留 + 安全余量
room = 窗口 - fixed - turn_peak_tokens()      # 还要扣当前轮 ReAct 的瞬时峰值！
by_turns = 想留的轮数 × 每轮稳态占用(单轮输入上限+输出上限)
sliding = min(by_turns, room)                  # 取两个数里小的
```

- **`turn_peak_tokens` 那一刀不能省**：ReAct 最多走 max_agent_steps 步，每步的 AI 消息和工具结果都同时挂在消息列表里喂下一步，瞬时占用比沉淀进历史的大得多。「这一轮跑不跑得起来」和「历史能留住几轮」分开记两个数，合成一个必有一边错
- **换模型只改一个「窗口多大」配置**，整张预算表跟着重算（查表前先剥 provider 前缀，硅基流动给的模型名是 `deepseek-ai/DeepSeek-V4-Flash`）
- **预算往两层分**：层 1 拿七成、层 2 拿三成。层 1 超了降级一批到层 2，层 2 超了在后台压成一段梗概
- **启动自检**：算出来连一轮都装不下，lifespan 打 error 报警，别等运行时撞墙

**中文 token 口径的坑**：常见估算默认四个字符折一个 token，照英文定的；中文一个字往往就是一个 token，默认口径算差好几倍。**口径和上限必须一起校准**：只校准口径，闸门一下收紧几倍，装得下的历史被白白裁掉；只调大上限，闸门看着松了实际发的还是超。更隐蔽的是方向必须全局统一——`chars_per_token` 是拿它当**除数**的，别处写「字数×校准值」两条路能差一倍多。凡拿字数换 token 的地方收口到同一个函数。

## 八、落到 LangGraph State：上下文随图一路走

- State 里 `messages` 字段挂 `add_messages` reducer，节点只管吐新消息，框架自动按序并入
- **立一条边界：State 里那份历史只进不出**。它是事实源，靠 checkpoint 落盘存着，中途断了能接着跑，事后复盘翻得到。分层从头到尾没碰它，动的是每轮调模型前**另外现拼的精简版**——两份各走各的
- **三层靠两个整数表达**：用户消息落库拿自增 id 带进 State（`HumanMessage(id=f"db-{msg_id}")` 锚点），摘要覆盖到哪条记一个 id，层 1 从哪条起再记一个 id：

```text
id ≤ summary_upto_msg_id          已进摘要，不再出现在窗口里
summary_upto < id ≤ layer1_from   层 2，渲染成半压形态
id > layer1_from                  层 1，原样
```

- **降级就是把后面那个 id 往后挪一格，一条消息都不用搬**。而且同一批消息渲染多少次结果都一样——边界稳住，发给模型的前缀逐字节稳定，缓存才保得住

## 九、代码走读要点

### 锚点与容错

- `_db_msg_id` 三层容错：没有 `id`、前缀对不上、解不出整数，一律返回 `None`——这是必要不是防御性编程，本章上线前的会话消息压根没这个锚点，checkpointer 里存着的老 State 读出来就是这样
- `_index_after` **只找 HumanMessage**：一轮从用户提问开始，从助手回复中间切进去，窗口开头会是一段没有问题的答案，模型读到半截悬空的上下文
- `return trimmed or window` 兜底不能省：`trim_messages` 在单条消息本身就超预算时返回空列表（用户粘一大段日志进来就是这种情况），宁可超预算发原窗，也不能给模型空消息列表，那必炸

### 层 2 压缩

```python
def compress_reply(text: str, keep_chars=None) -> str:   # 客服答复留头部
    ...
    return text[:n] + "…(略)"

def compress_tool_result(name: str, content: str) -> str:
    if chars_to_tokens(len(content)) <= settings.layer2_tool_keep_tokens:
        return content
    return f"(已调用 {name or '工具'},结果从略)"
```

- 工具结果按大小分开处理：订单字段一百多字原样留（下一轮追问还用得上），检索证据三千多字压成一行（那份证据是某一轮答某个问题用的，答完就不该再占位）
- **渲染必须保留原 `id`**（id 是切窗锚点，丢了下一轮定位不到）
- **AI 消息上的 `tool_calls` 必须原样带上**（踩过的坑）：压的是正文不是这一轮的调用结构，后面那条 ToolMessage 拿 tool_call_id 指着它，新建 AIMessage 时漏掉 tool_calls，这对引用就断了，上游直接回 400「tool result's tool id not found」整轮挂掉。造测试数据时容易只写 content，这个洞能一直藏着直到真被接进请求路径才炸
- 这些函数幂等：同一批消息渲染多少次结果一样——降级随时重算，不必记状态

### 摘要两种形态

- `summary_line`：coref/意图用，压成一行前缀 `(早前对话摘要:...)` 塞纯文本历史最上面
- `summary_system`：名字带 system 但返回值**从来没当 system 用过**——主力 Agent 只取 `.content` 并进本轮材料那条 HumanMessage。两处无摘要都返回空值，调用方拿到空跳过
- 那句「其中事实可信」是写给模型看的：不点明，模型容易把摘要当可疑的二手转述，答题反而绕开它

### 上下文日志

每轮调模型前把实际发出去的内容打进日志：`model_ctx`（摘要全文 + 滑窗每条角色+前 40 字 + 窗口条数 + token 估算）、`history_ctx`（coref/意图共用）。上下文管理最难受的地方是看不见——模型答得不对劲，你不知道是它笨还是当时喂进去的东西不对，而喂进去的东西是每轮现拼的，事后翻不出来。

那个 `TURN_CTX_ID` 哨兵挂在 `id` 上，**不能挂 `name`**：name 会被序列化发给上游、改变请求字节，等于亲手把刚修好的缓存前缀又搞乱。

### 摘要任务细节

- **摘要边界就是层 1 起点**（`layer1_from_msg_id`），不用另算一套。第一版按轮数算边界是双层时代的遗产，改成从窗口倒推后两者脱节：按轮数那条每次都比层 1 起点伸得更远，一口把还在层 1 的内容吞掉，层 2 永远为空——**跑起来只有两层**。这种错法特别难发现：锚点在动、日志在打、摘要在落库，从外面看一切正常，只有把渲染出来的消息列表逐条摊开才看得出层 2 压根没被压过
- `from_msg_id` 取 `old_upto + 1`，段与段首尾相接不留缝不重叠
- **摘要压出来是空的就抛异常不写库**——写进空段落，锚点照样往前推，那批对话等于凭空蒸发，比不压还糟；这种「静默地把好数据换成坏数据」最难查
- **投影读取必须在 `s.add(新段)` 之前**：反过来 SQLAlchemy 的 autoflush 会把还没提交的新段也算进查询，拼投影时它出现两次——段落表本身是对的，只有拼好的那一列多了一行
- `maybe_schedule_summary` 挂 run_turn/stream_turn 末尾，`create_task` 后不 await；两次 `in _running` 检查中间隔着两个 await，协程让出控制权时并发触发可能起双任务，**入表前再查一次**（TOCTOU）
- `_done` 回调先确认 `_running.get(cid) is t` 再 pop——直接 pop 会把登记晚的新任务抹掉，防抖失效
- **整个函数体 try 包住**：在用户回复路径上，抛出去会把正常回复带崩；摘要没跑成无所谓，触发条件还在下轮重来
- 多副本部署时同会话可能两个进程同时触发、各自算出不同边界，`_running` 进程内字典要换数据库行锁

### 演示配置

想看摘要链跑起来，光调窗口不够（固定开销和单轮峰值按默认 X、Y、步数算，只把窗口压到两万 room 直接负数，启动自检报「上下文预算不足」），得连着一起压：

```bash
MODEL_CONTEXT_WINDOW=18000 MAX_OUTPUT_TOKENS=2000 MAX_USER_INPUT_TOKENS=2000 \
MAX_AGENT_STEPS=3 TOOL_RESULT_MAX_TOKENS=1200 RERANK_TOP_K=5
```

算出来滑窗 5650、层 1 预算 3954、层 2 预算 1695，二十来轮撞第一次降级、再聊十几轮层 2 攒满摘要起来。

**默认窗口下不该触发任何降级和摘要**——装得下就不压，压缩是成本不是美德，这一条也要验。

## 十、实战要点

功能需求七条：① 三层结构（层 1 原文保真/层 2 规则截短/层 3 异步摘要，两个锚点划边界、降级只挪 id 不搬数据，分段摘要表一段一行只追加）；② 摘要后台异步（触发看用量不数条数，摘要 prompt 只提炼事实诉求、一字不编、寒暄不留）；③ 拼装顺序固定（system 打头每轮一样，摘要证据合成一条挂用户句后，梗概不许单独占 system——前缀缓存整段作废）；④ token 预算从窗口倒推（扣固定开销+ReAct 瞬时峰值，层 1 七成层 2 三成，启动自检，中文口径和预算一起校准）；⑤ 对话历史落 conversations/messages 两表，State messages 挂 add_messages reducer + checkpoint 存全量，调模型前另拼精简版，双轨互不影响；⑥ 上下文可观测（model_ctx/history_ctx 每轮必打，后台摘要任务全留痕）；⑦ 前端多会话侧栏（两个只读接口，侧栏失败静默降级不影响聊天）。

验收五条：① 连续聊二十轮以上 token 不爆系统不崩；② 演示配置跑一遍日志能看到完整级联（层 1 降级 → 层 2 起摘要 → 落新段），这时问「最开始那个订单后来怎么说」能靠梗概里存下的订单号和诉求答对；③ 默认窗口聊二十轮不该触发任何降级和摘要；④ 日志能看到早期轮次被后台压缩、且没阻塞当轮回复，grep model_ctx/history_ctx 直接可看；⑤ 前端侧栏多会话对照、切回旧会话历史完整回载接着聊。

**关键决策**：摘要**三处注入**（main_agent、指代消解、意图识别都能看到——跨滑窗指代「最开始那个订单」才能被改写/判对）；边界对齐走**方案 B**（State 带 DB id 锚点，精确对齐、纯函数、不加库读）；最终验收**全浏览器手动**（用户亲手聊 20+ 轮）。

## 十一、本章小结

- **三种选法**：滑窗打底保时效、语义检索捞远处相关、关键事实单独留底；本课量级只把滑窗做扎实
- **分层落地**：层 1 原文保真 → 层 2 规则截短（用户原话不动、答复留头、工具结果按大小分）→ 层 3 异步摘要；越近越完整，越远压得越狠
- **一段段攒**：压完定死不回炉，一个事实只经历一次压缩
- **缓存**：整条列表只有一条恒定 system；可变内容一律不许进 system，否则前缀全 miss（实测归零）
- **预算**：窗口 - 固定开销 - 瞬时峰值，层 1 七成层 2 三成；中文 token 口径和上限一起校准、方向全局统一
- **State 双轨**：全量历史只进不出 + 每轮现拼精简版；两个 id 锚点划边界，降级挪数字不搬数据
- **边界**：只管当前这通会话，不跨会话、不攒画像

## 附：本章踩坑记录

| 坑 | 现象 | 解法 |
|---|---|---|
| 摘要进 system | 缓存命中数直接归零 | 摘要跟证据一起挂用户句后，全列表只留一条恒定 system |
| 摘要漏 tool_calls | 上游回 400「tool result's tool id not found」 | 压缩 AI 消息必须原样带 tool_calls，压的是正文不是调用结构 |
| 边界用轮数算 | 层 2 永远为空，跑起来只有两层 | 摘要边界 = layer1_from_msg_id（层 1 起点），别另算一套 |
| 投影读到新段 | 拼好的 summary 列多一行，段落表本身对 | 投影查询放在 s.add 之前（autoflush 会把未提交段算进去） |
| 空摘要照写 | 那批对话凭空蒸发无报错 | 摘要为空抛异常不写库 |
| 双起摘要任务 | 同会话并发触发起两个任务 | await 之间 TOCTOU，入表前再查一次 _running |
| done 误清登记 | 新任务登记被旧任务 pop 抹掉 | _done 先确认 _running.get(cid) is t 再 pop |
| 中文 token 低估 | 默认四字符折一 token，中文差出几倍 | 薄封装统一入口，口径和上限一起校准 |
| 拿同问题验缓存 | 测不出改动效果 | 拿不同问题各开会话，看 cache_read 复用量 |
| 只调窗口压摘要 | room 负数、滑窗归零、自检报警 | 固定开销和峰值按默认算，演示配置要连 X、Y、步数一起压 |
