# RepoLaunch 的工作流：哪些决定交给模型

**日期**：2026 年 10 月 28 日

做部署助手时，一个很容易出现的想法是：把仓库交给模型，让它自行决定所有安装和启动操作。问题在于，用户最后需要审阅的是一份可以执行、可以解释、可以复查的方案。

这一版选择先固定流程，再让模型填充受支持的决策。模型擅长从 README、依赖声明和代码线索里提出候选解释；程序负责检查解释是否落在执行器能处理的范围。

## 图中只有三个主要节点

源码中的核心连接可以缩写为下面几行，省略了初始化和追踪配置：

```python
builder.add_node("retrieve", self._retrieve)
builder.add_node("propose", self._propose)
builder.add_node("validate", self._validate)
builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "propose")
builder.add_edge("propose", "validate")
builder.add_edge("validate", END)
```

这张图不会动态寻找新工具，也不会无限循环尝试。普通规划和失败修复复用这条路径，区别在于状态里有没有旧方案和真实失败日志。

## 检索阶段提供参考，不能取得执行权限

检索器根据仓库或日志信息找诊断案例。案例可以帮助模型识别缺少依赖、入口问题等常见情况，但它们只是参考数据。

同样，README 里的命令和注释也不能直接成为系统指令。仓库文本、日志和检索内容都需要按不可信输入处理；执行器接受的是通过校验的结构化字段。

## JSON 能解析，只是第一步

模型返回内容之后，系统需要依次确认：

1. 返回值是不是完整 JSON，是否存在重复键或无效常量。
2. 字段名、类型和取值是否符合约定。
3. 入口与路径是否处于允许的仓库范围。
4. 运行形式是否属于执行器支持的种类。
5. 如果是修复，是否改变了本来应该保持的字段。

因此，“模型按要求返回了 JSON”和“这份方案可以运行”是两个不同的判断。后者还要经过字段约束和实际执行验证。

## 为什么审批放在图外

规划结束之后，用户应看到依赖、入口、风险和验证路径，再决定是否执行。一次修复改变了部署方案，也需要再次确认。

审批不能只是一句提示词。它需要由任务状态和 API 流程落实，否则模型口头说“请确认”，程序仍可能已经开始安装。

没有模型配置时，系统有显式标记的规则模式。规则模式是可用的降级路径，但界面和报告应明确它没有发生模型调用，避免把规则结果展示成 Agent 推理。

## 这种设计的代价

固定字段降低了表达能力。复杂构建脚本、特殊操作系统包和多服务依赖，可能无法在这一版中表达。与其把支持范围藏在一段任意命令里，更容易维护的方式是先记录失败类别，再根据真实需求扩展执行器。

下一步值得改进的是失败分类与评估集，而不是单纯给图增加节点数量。
