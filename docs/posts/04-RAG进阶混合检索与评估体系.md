**日期**：2026-06-24
**标签**：AI Agent · RAG · 混合检索

> 上一章的向量检索能听懂「邮费」了，但用户一句「BE200 支持快充吗」又翻车：库里躺着 BE200 和 BE100 两份参数表，八成字句一模一样，唯一差别就是型号那几个字符。向量检索看整段意思，两份文档意思差不多，型号这种没什么语义的字符反而排不上号——上一代的参数表堂而皇之排到前面，回答跟着把快充功率报错了。这一章：给向量补一条「认字面」的路，再把「排得准」单独拎出来做，最后用一套评估体系让每一招都拿数字说话。

## 一、BM25：给向量补一条字面路径

### BM25 怎么打分

信息检索领域用了几十年的标准关键词打分算法（搜索引擎、Elasticsearch 都建在它上面）。逻辑不复杂：**query 的词在某文档里命中得越多、命中的词越稀有，分越高**。「的」「是」到处都有所以不重要，「花呗分期」这种少见词命中一次几乎锁定答案。

老算法 TF-IDF 也有这个思路，BM25 补了两处修正：

1. **词频饱和**：促销规则里「满减」出现十次，不代表相关度是出现一次的十倍——出现到一定次数后加分放缓，防堆词文档占便宜
2. **文档长度归一化**：长手册天然包含更多字，不能因为长就更容易命中，按长度打折扣，让长短文档同一起跑线

两处各有一个参数控制，用默认值起步、拿评估集微调即可。

### 短板互补：谁也替不了谁

| | 认什么 | 短板 |
|---|---|---|
| BM25 | 字面 | 「退货」和「退款」是毫不相干的词，不知道说的是同一件事 |
| 向量 | 语义 | 型号编号、SKU 这类「没什么语义」的字符认不准 |

两条路径短板刚好相反，**从此并存着走，不是拿一条换掉另一条**。

## 二、落点：还是 Milvus，一库两路

Milvus 2.5 起自带 BM25 全文检索。建库时给正文字段挂一个 BM25 Function，Milvus 自动生成稀疏向量，中文分词走内置 `chinese` analyzer（底层 jieba），不用自己接分词。dense 向量和稀疏向量在同一张集合里并排存。

查询时一次 `hybrid_search` 把两路一起要回来（用 pymilvus 下沉一层看原理；LangChain 那层也能做，只是封装了细节）：

```python
from pymilvus import MilvusClient, AnnSearchRequest, RRFRanker

client = MilvusClient(uri="http://localhost:19530")
dense_req = AnnSearchRequest(
    data=[query_vector], anns_field="dense_vector",
    param={"metric_type": "COSINE"}, limit=50,
)
sparse_req = AnnSearchRequest(
    data=[query_text], anns_field="sparse_vector",
    param={"metric_type": "BM25"}, limit=50,
)
results = client.hybrid_search(
    "ecommerce_kb", reqs=[dense_req, sparse_req],
    ranker=RRFRanker(k=60), limit=50,
)
```

两条请求各先要回 50 条候选，`hybrid_search` 送进 `RRFRanker` 融合，吐出一份候选池——这是**粗排池**，后面的精排再收窄到十条左右送去生成。

**业界另一条路线**：BM25 单独交给 Elasticsearch（全文检索基建和中文分词更老到），适合已有 ES 集群或要独立扩展全文检索的团队；我们一库两路省下整套 ES 运维，数据一致性也不用在两系统间对齐。面试提一句即可。

## 三、三阶段流水线：先捞得全，再排得准

| 阶段 | 干什么 | 关键词 |
|---|---|---|
| **召回** | 向量和 BM25 各独立跑一遍，各捞 50 条候选；检索前先按元数据（品类、店铺）筛一圈缩小范围 | 捞得全 |
| **融合（粗排）** | 把两路结果合成一个候选池，排序粗糙 | 打底稿 |
| **精排** | 用更准但更慢的模型（reranker）把候选重新细排，只留 Top-10 交给生成模型 | 排得准 |

- 召回阶段按元数据先筛：候选池干净了精度提升、多数时候更快；但**过滤条件卡太窄时带过滤的向量检索反而变慢**
- 融合权重可按 query 类型定：型号、优惠券代码这类标准化用词偏 BM25；口语化模糊问法偏向量

## 四、两套分数怎么合：加权还是拼排名

- **分数级融合**：两套分各自归一化到同一区间再按权重加。可控但权重得逐场景手调
- **RRF（倒数排名融合）**：不比分数只比排名——每份文档在每条排序里贡献 `1/(k+排名)`，k 通常取 60，两边都靠前的文档自然冒头。完全绕开分数量纲不统一，开箱即用，眼下最常见

向量余弦相似度是 [-1,1]，BM25 是几分到十几分的无界数，**直接相加没有道理**。

## 五、粗排也会看走眼：精排登场

用户问「退货运费谁承担」，库里两条相关条款：「退货规则：七天无理由退货，未拆封可退」（字面「退货」出现多次）vs「运费险：未购买运费险，退货产生的运费由买家承担」（真正答了题但字面命中少）。粗排只数字面，把前者排前面，交给模型就顺着退货流程说一堆，不提运费谁出。

### Cross-Encoder vs Bi-Encoder

| | 结构 | 特点 |
|---|---|---|
| **Bi-Encoder（双塔）** | query、文档各自独立编码成向量，再比相似度 | 文档向量可提前算好存起来，检索极快；两边编码时互不知道对方问什么，精度有上限（BGE-M3 就是双塔） |
| **Cross-Encoder（交叉编码）** | query 和文档拼成一条输入，每词充分交互 | 读出「运费该谁出」这种深层关联；精度高但跑不动大规模，要逐对现算 |

各司其职：双塔在海量候选里快速筛，交叉编码在一小把候选里挑最准的。

### reranker 选型

- 中文/中英混合场景默认 **bge-reranker-v2-m3**——跟 BGE-M3 同系列同底座，中英双强，生产踩坑资料好查；更强的对照拿 Qwen3-Reranker 上自己的评估集比
- **被忽略的细节**：reranker 最大输入长度要跟 chunk 大小对齐——chunk 比它还能处理的还长，尾部被悄悄截断，精排等于白做

### 精排排序完还要防 Lost in the Middle

LLM 读长上下文对中间位置内容利用率最低。就算精排把最相关的捞出来了，埋在候选中间模型也视而不见。所以**精排的价值不只是把对的排进候选池，更是把最相关的几条摆到最前和最末**，刻意避开注意力盲区。

### 精排慢，三招压延迟

1. **缩小候选数**：候选数直接决定要跑多少次模型
2. **批量推理**：几十对 query+文档打包一个批次送进模型，别写循环一条条来
3. **模型量化**：INT8 低精度 + 专用推理引擎，精度损失不大速度提升明显

## 六、为什么不能精排扫全库

Cross-Encoder 要把 query 和每一份文档拼在一起现算，几十万条跑一遍慢到用户等不起。所以先召回把候选池收窄，精排只在池上发力。

**候选池大小是召回率的上限**——正确文档没进池，精排再准也救不回来，宁可先调大保住召回。交给生成模型的条数同样有讲究：太少漏信息，太多塞噪音还拖慢生成，拿评估集找到刚好够用的数。

## 七、Query 理解：问题问得好，检索才有戏

| 手段 | 做法 | 目标 |
|---|---|---|
| **Query 改写** | 「这个是不是能便宜点买」→「是否支持优惠或满减」，贴近知识库表达 | 求准（一句变一句） |
| **Query 扩写** | 加同义词/相关词，变成多条查询一起查（优惠/满减/折扣） | 求全（一句变三句） |

两个目标维度不同，别用同一套逻辑衡量。

- **同义词只补 BM25 侧**：BM25 是词面匹配，多几个近义词纯赚（用户说「邮费」文档写「运费」，正好补缺口）；向量编码整句语义，标准问法后缀一串同义词会带偏语义重心，反而变差
- **HyDE**：先让模型编一段「可能的答案」，把假答案向量化去检索真实文档。假答案是编的也没关系，用它的语义丰满度——完整答案自带一堆相关术语，向量比简短提问更接近答案文档。代价是多一次模型调用，强 Embedding 下可能负优化，要实测
- **入库侧别拆多份**（大坑）：把一条知识泛化成多个问法、按一问一答存成多条记录——同一条知识产生多条高度相似的向量，一个 query 进来 Top-K 名额全被这同一条的变体占满，别的知识挤不进候选池。**扩召回在检索侧做 Query 扩写，用完就丢；库里每条知识只存一份**。入库侧增强召回走「给每块补上下文再嵌入」，不是拆多份

## 八、生成前后的几道闸：查到了不等于答对了

### 闸 1：生成前立规矩

system prompt 把身份、硬约束、红线一次交代：只依据【知识片段】回答；每条结论标来源编号 [1][2]；负面清单（不承诺到货时间/物流时效/退款金额裁定）。

**负面清单为什么非写死不可**：到货时间、物流时效、退款金额这类话被模型顺口答出去，客服系统就替公司做了承诺，用户真照着主张权益出了问题没法收场。宁可啰嗦，别留松口余地。

### 闸 2：生成后溯源验证

- **prompt 边答边标** `[编号]`：最简单，但会漏标、标错
- **NLI 后处理**：回答拆成一句一句，逐句查原文能不能支撑，支撑不住的大概率是编的。更可靠，代价多跑一趟 Review
- 生产通常两条一起上；编号映射到 chunk 的 `section_path`，点编号跳回原文核对：

```json
{
  "answer": "支持 7 天无理由退货，定制类商品除外 [1]；未买运费险时，退货运费由买家承担 [2]。",
  "citations": [
    { "mark": "[1]", "section_path": "退货政策 > 无理由退货" },
    { "mark": "[2]", "section_path": "运费险 > 退货运费" }
  ]
}
```

### 闸 3：该拒答就拒答

检索不到/置信度太低，老实说没查到转人工。让模型**生成之前先自评**：知识够不够答，够就 `useful=true` 正常生成，不够就 `useful=false` + 兜底话术。判不能的原因拆开存：

```json
{
  "useful": false,
  "reply": "这个问题暂时没查到明确依据，已经为你转接人工客服",
  "reason": "检索资料只覆盖站内支付方式，没提到跨境订单的退款到账周期",
  "route": "human_handoff"
}
```

`useful=false` 的自动沉进**问题池**（数据飞轮章的入口），`reason` 留复盘线索。

## 九、RAG 评估体系：有没有变好，得拿数据验证

光靠「感觉」调参是拍脑袋。需要评估集（一批事先标好标准答案的测试题）+ 分层指标。

### 指标分层

| 段 | 指标 | 含义 |
|---|---|---|
| 检索段 | **Recall@k** | 正确的资料有没有出现在前 k 个结果里 |
| 检索段 | **MRR**（平均倒数排名） | 正确资料排第 1 得 1 分、排第 2 得 0.5 分，没召回记 0，取平均——看排得靠不靠前 |
| 检索↔生成之间 | **证据覆盖度** | 标准答案拆成几个要点，数检索回来的资料字面盖住几个。纯字符串匹配、不调大模型、可复现，预告生成段答得全不全 |
| 生成段 | **LLM-as-Judge 答案覆盖度** | 拿另一个模型当裁判照标准打分，看答案覆盖几个标准要点 |
| 生成段 | **Faithfulness** | 答案有几成能在检索原文找到依据，专抓「资料里没有、模型自己编」的幻觉 |

自建评估而非 RAGAS：要四种策略横向比、按桶拆开看、算机械证据覆盖度和拒答率，定制化。

### 评估集长什么样

```json
{
  "id": "B1",
  "bucket": "B_model",
  "query": "MH-LP100 的废砂盒多久倒一次",
  "expect_section": ["MH-LP100"],
  "expect_points": ["5 至 7 天", "7 天(单猫)"],
  "should_refuse": false
}
```

- `bucket` 分桶：政策类 A / 型号精确匹配 B / 口语模糊 C / 跨文档 E
- `expect_section` ground-truth：正确答案该来自哪一节（检索段看 section_path 命中/名次）
- `expect_points`：标准答案要点（证据覆盖度/答案覆盖度数盖住几个）
- `should_refuse=true` 的题（该拒答的）：expect_section/expect_points 留空
- 抽部分人工校验，确认标注要点真能在原文对上
- **不能全是好答的题**：该拒答的、刁钻的都得有

### 排查思路

回答不满意 → 先看检索段：Recall 低 = 该找的没找到，问题在**切分/检索**，调 prompt 没用；Recall 高但证据覆盖度上不去 = 排序不对，真正答题的被挤后面，该下功夫**精排**；检索数字都漂亮但生成不行 = 问题在 **prompt 设计或模型本身**。

## 十、四策略对比：两个反直觉结论

300 道自建评估题、51 个知识库小节，四策略各跑一遍（纯向量 / 纯 BM25 / 混合 RRF / 混合加精排），从检索排名比到证据覆盖度、答案覆盖度，再按 query 类型分桶：

1. **BM25 未必输给向量**：电商客服里用户问法看着随意，但涉及型号、优惠券、SKU 时用词相当标准化——这种 query 上 BM25 可能反超向量。谁强谁弱看 query 特征，不能一概而论
2. **混合检索不是「多一路总归更稳」**：口语类问题上纯向量单独满分，一融合 BM25 反而掉——RRF 按排名算分不看两路谁更可信，BM25 在这类问题上本来就弱，融合进来的噪声把向量排对的答案往后挤。**真正填坑的是精排**（不看排名、重读内容重打分），口语类冲回满分双双反超

第二条结论比「谁最强」更值钱：**混合检索要兑现收益，精排不能省**。

规模声明：300 题 51 小节不大，图的是课程环境秒级验证；知识库到成百上千类目、上万条记录，结论得回自己数据重跑。

## 十一、代码走读要点

### 冒烟多验一件事

`smoke_rerank.py` 不只验通不通，还验**排出来的第一名对不对**（喂三条文档问「退货运费谁承担」，讲买家承担的那条必须排第一）——接口返回 200 但排序没用比接不通更难发现。细节：地址拼法从应用代码 import（别各拼各的）；payload 形状必须跟应用真发的一模一样。

### 集合重建

- `text` 字段 `max_length=16384`（不是照抄 answer 的 8192！text = category+questions+answer 拼接恒长于 answer，照抄长块 upsert 溢出——真实踩过）
- `enable_analyzer=True` + `analyzer_params={"type": "chinese"}` 缺一不可——默认按空白标点切词，中文进去切不动，BM25 权重没有意义
- 两套索引挂同一集合：dense 走 COSINE，sparse 走 `SPARSE_INVERTED_INDEX` + BM25

### acall：集成期踩得最深的坑

pymilvus 是同步库（底下 gRPC），async 服务里直觉丢 `to_thread`——同一客户端被多线程共享，**间歇性返回空结果**：不抛异常不报错，就是查出来是空的，下一次又正常。最难的故障，不稳定复现、日志无异常。

解法：所有 Milvus 调用固定到一个专用线程（`ThreadPoolExecutor(max_workers=1)`），客户端也在这个线程里惰性创建——**两件事必须配套**，只挪调用、客户端还在主线程建的话共享问题原样存在。代价是 Milvus 调用串行化，但比重建客户端+连接池划算。

### rerank 客户端

- 手写 httpx，不用 openai 客户端——重排不在 OpenAI 协议里，走 Jina/Cohere 那套（进 `query`+`documents`，回 `results` 带 `index`+`relevance_score`）
- 返回值 `[(原始索引, 相关分)]`：index 是入参 documents 的下标，调用方拿下标回自己列表取元数据，重排层不知道知识块长什么样
- `_rerank_url`：各家版本段不统一（硅基流动/Jina 在 /v1，Cohere 在 /v2），地址没版本段就补 /v1——这个错不在启动时暴露，服务照常起来，走到重排那一步才 404，排障要倒推一圈
- 重试只留 429 和几个 5xx（瞬时限流退一步就过去）；4xx 参数错误不进集合，重试一百次结果一样
- **不静默算低分**：评估一轮打两千多次上游，一次限流失败被吞掉返回空列表，这道题被记成召回失败，分数比真实低且没人知道为什么——让它抛出去记成错误，至少「分数可疑」是明确的

### Query 理解

- `r.standard or query` 兜底不能省：改写是检索链入口，模型偶尔返回空串，兜不住整条链断在第一步
- 结构化输出用扁平字段（list[str]），绕开上游对嵌套对象数组的 502
- **同义词只进 bm25_text**：`query` 永远拿去向量化，`bm25_text` 只喂 BM25——两个独立参数，靠接口设计不靠约定

### 检索编排

- 四策略 `vector / bm25 / hybrid / hybrid_rerank`，线上只用最后一种；前三种是评估的对照柱——没有对照就说不清「加重排提升多少」
- **split_clauses 子句拆分**：「我在新疆下单 80 块钱，运费怎么算，会员免运费能不能抵」一句话问三件事，整句向量化语义重心只落一个意图，另外两个连前十都进不去；拆开各查一遍轮转合并。注意 `_MIN_CLAUSE=4` 挡碎片（「怎么办」三字毫无信息量）。**适用条件**：子句各自第一名要够准合并才有意义——实测重排 +0.02、其余三路 -0.04~-0.06，没有精排把关拆完只是把噪声乘以三
- `_merge_round_robin`：各子句轮流出一条，保证每个意图前排都有位置；同一小节多子句命中挪到 tail 排最后（扔可惜、连占三个名额挤掉别的意图）
- `arrange_head_tail`：三行代码，把最相关放首、次相关放尾，其余居中——改喂进 prompt 的顺序不改内容

### 两道证据闸

- **机械闸**：无召回 or 重排最高分 < `rerank_min_score=0.3` → `sufficient=False` + `source=retrieval_low_conf`。`source` 字段区分「检索就没召回到」vs「召回了自评说不够」，补救动作完全不同
- **语义闸**：生成前让模型自评证据够不够（`check_sufficient`）→ `source=self_check`。闸设在生成前：判不能直接拒答省一次生成调用；生成完再判，钱已花且容易「勉强用一下」。prompt 必须写「严格只看证据是否够答，不要脑补证据外的知识」——自评模型天然拿常识补全，一补闸就架空
- **品类过滤要能退回来**：category 是模型自由填的，常猜错入库值（「商品手册」≠ 实存「商品规格手册」），精确过滤把结果清空导致误拒答。定位改清楚：**过滤是优化不是硬约束**，滤完为空/最高分过不了阈值就退回去不带过滤重查
- **编号证据**：`arrange_head_tail` 在编号前调用，所以角标顺序=喂模型顺序，答案 `[1]` 对应 `citations[0]`，前端点角标直接翻回原文

### 低置信池

```sql
source ENUM('retrieval_low_conf','self_check','user_feedback')
```

三个入口对应三种「答不了」：检索没召回到 / 召回了自评不够 / 答了用户说没解决。哪些问题反复被问又反复答不了，就是知识库该补的地方。本章只管把 `sufficient=False` + `source` 传出去，落池动作在下一章编排。

### 评估脚本的坑

- **检索深度跟线上对齐**（`K=10` = 线上 `rerank_top_k`）——评估用 20 线上用 10，量出来的是一个不存在的系统
- **MRR 口径**：跨文档题按「每块证据各自名次倒数取平均，漏的记 0」，不用「最后一块到位的名次」——两块证据的题最好情况上限只有 0.5，是口径带来的不是检索变差，画同一张图会误读
- **评估里生成端必须固定**：四策略共用同一个生成器，答案差异才算得到检索身上；线上生成规则挂 AGENT_SYSTEM，评估的 RAG_ANSWER_PROMPT 独立，刻意不共用
- **faith_cases 台账表**：忠实度裁判判出的每条编造单独进表，跨轮追溯（报告重跑就被覆盖，个案价值在跨轮）——同一道题反复被判编造说明库那格一直没补对；`uk_eval_id` 一题一行，seen_count 累计；标「已解决」又复发自动退回未解决；citations 存当轮证据全集不只被引用的
- **并发压 5**：限流按 key 全局算，评估开到 20 并发快，代价是同时用应用的人全部撞 429——跑评估别把别人的请求挤掉

## 十二、实战要点

功能需求七条：混合检索（BM25 Function + chinese analyzer + hybrid_search RRF）；重排 bge-reranker-v2-m3 出 Top-10、最相关放首尾；元数据过滤；Query 理解（改写归一 + 同义词只在检索侧）；生成质量控制（引用编号可溯源、证据不足拒答、生成前自评 + 低置信池、负面清单）；评估体系（Recall@K/MRR/Faithfulness，四策略分桶报告）；前端（引用编号可点击看来源 + 满意度 👍/👎 反馈，先纯前端采集给飞轮留入口）。

验收标准四条：① 四策略对比报告能跑出数字；② 带具体型号的问题 BM25 能命中；③ 答案引用编号能定位回原文、聊天页点引用看到来源；④ 知识库没有的内容明确拒答且问题进了低置信池。

## 十三、本章小结

- **混合检索**：BM25 认字面、向量认语义，短板互补；同一 Milvus 一库两路，hybrid_search + RRF 融合
- **三阶段**：召回图快图全 → 融合粗排打底稿 → 精排图准定顺序；少了任何一段要么慢得离谱要么准头不够
- **精排**：Cross-Encoder 重读内容重打分，输入长度对齐 chunk；最相关放首尾防 Lost in the Middle
- **Query 理解**：改写求准、扩写求全；同义词只补 BM25；扩召回放检索侧，库里一份知识一份存
- **质量闸**：生成前立规矩、生成后溯源、该拒就拒（useful=false 落问题池）
- **评估**：分层指标（Recall@k/MRR/证据覆盖度/答案覆盖度/Faithfulness）+ 分桶评估集，每一招上线前拿数字验证
- **两个反直觉**：BM25 在标准化用词上未必输向量；混合检索要兑现收益精排不能省

检索这条线至此完整。下一章：一次问答不止一步的时候，谁来决定下一步做什么——Workflow + Agent 混合架构。

## 附：本章踩坑记录

| 坑 | 现象 | 解法 |
|---|---|---|
| rerank 排序没用 | 上游 200 但排出来第一名是错的 | 冒烟不只验连通，喂标注样例验第一名 |
| text 字段溢出 | 长块 upsert 报错 | text 是拼接结果恒长于 answer，放宽到 16384 |
| 中文 BM25 无效 | 分析器默认按空白切词，中文切不动 | enable_analyzer + chinese analyzer 缺一不可 |
| Milvus 间歇性空结果 | 不报错不抛异常，查出来是空的 | 单线程专用执行器 + 客户端同线程创建，配套 |
| rerank 404 | 回答质量不对，倒推发现是地址没版本段 | _rerank_url 补 /v1，每次现算改配置不用重启 |
| 同义词污染向量 | 标准问法后缀同义词，检索结果变差 | query 只向量化，同义词只进 bm25_text |
| 子句拆分反而更吵 | 无精排路径上拆完变差 | 拆分配精排用（+0.02），其余路径 -0.04 |
| 品类过滤误拒答 | category 猜错入库值，结果清空判拒答 | 过滤当优化不当硬约束，为空回退重查 |
| 自评模型脑补 | 拿常识补全证据，闸被架空 | prompt 写死「严格只看证据，不要脑补」 |
| MRR 口径误导 | 跨文档桶天生低一半被误读成变差 | 按每块证据各自名次倒数平均，漏的记 0 |
| 评估吞限流错误 | 记成召回失败分数偏低且无人知道 | 让异常抛出去，分数可疑这件事明确 |
