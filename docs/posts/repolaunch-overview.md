# RepoLaunch：从仓库到可验证的本地运行

**记录阶段**：2026 年 10 月下旬 · 10 月 28 日整理

找到一个感兴趣的开源项目之后，真正运行它往往还需要确认 Python 版本、依赖文件、启动入口和额外服务。README 给出了线索，但不同仓库的约定并不统一。

RepoLaunch 把这段过程组织成一个本地任务：读取仓库、生成方案、等待审阅、尝试部署，再用实际响应检查结果。发生失败时，日志会进入诊断流程，修复建议仍要经过校验和确认。

## 把首版范围缩小之后，才容易判断成功与失败

这一版面向公开、CPU 运行的 Python Web 仓库。它不接管用户电脑上任意软件的安装，也不承诺运行所有 GitHub 项目。

限定范围后，部署方案可以写成固定字段，例如 Python 版本、依赖安装方式、模块入口、端口和检查路径。程序只支持明确列出的运行形式，模型不能随意生成一个 shell 脚本交给宿主机执行。

这个取舍会拒绝一些复杂项目，但能让用户看到“准备运行什么”，也让验证和排错有清楚的对象。

## 一次任务怎样往下走

```text
仓库地址
  → 校验仓库范围，固定提交，读取必要文件
  → 检索案例，生成结构化方案，校验字段
  → 用户审阅确认
  → 构建镜像，启动独立容器
  → 检查 HTTP 响应，记录日志与结果
  → 失败时提出受控补丁，再确认、再验证
```

仓库提交需要固定下来：如果每次取默认分支最新代码，前一次成功和下一次失败可能根本不是同一份输入。这个提交会进入任务与复现材料，方便之后对照。

## 各层实际负责什么

| 层 | 责任 | 入口 |
| --- | --- | --- |
| FastAPI 与页面 | 接收任务、展示方案、处理确认与取消、导出报告 | `repolaunch/app.py` |
| LangGraph 规划 | 案例检索、模型建议、结构校验 | `repolaunch/planner.py` |
| 执行引擎 | 仓库读取、Docker 命令、端口与 HTTP 检查 | `repolaunch/engine.py` |
| 记录与集成 | 持久化任务、检索故障案例、追踪模型请求 | `storage.py`、`knowledge.py` |

Docker 承载目标项目的依赖和运行进程。运行时设置普通用户、资源限制、权限限制，并把端口发布到本机回环地址。构建过程仍可能下载依赖，这一版只用于受信任项目的本地开发验证。

## 现在保留了哪些证据

2026 年 10 月 26 日的验收记录包含三个选定公开仓库的真实部署，以及一次故意缺少 requests 的失败修复。对应结果保留在项目文档中，而不是只在页面上显示一个“成功”。

这还是小样本验证。目标项目需要密钥、GPU、多服务 Compose 或源码级修改时，当前流程会遇到边界，不能把它们算成已支持。

另外，固定仓库提交只固定了一部分输入。基础镜像和依赖版本如果仍有浮动，就不能宣称环境完全可复现。
