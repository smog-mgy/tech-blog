# 模型提出补丁之后，程序还要检查什么

**日期**：2026 年 10 月 28 日

“修复成功”需要发生在重建和验证之后。模型提出了一个看起来合理的依赖名称，并不能说明目标服务真的恢复了。

2026 年 10 月 26 日，验收样例先故意构建一个缺少 requests 的镜像，再观察真实的 `ModuleNotFoundError`。这使修复流程有一个已知、可重复的故障对象。

## 先取得真实错误，再生成建议

失败容器的日志需要在清理前保存。否则后续诊断只剩下“进程退出”，模型既不知道缺少哪个模块，也无法解释为什么建议安装某个包。

这一版把截取后的日志、原方案和诊断案例交给规划器。案例是提示，真正支持“补充 requests”这个操作的证据，是目标进程确实报告缺少该模块。

## 为什么修复只返回补丁

如果让模型重新生成完整方案，它可能在补依赖的同时换掉入口、端口和检查路径。即使新方案启动成功，也很难判断到底修好了原问题，还是绕开了原来的目标。

修复补丁的格式如下：

```json
{
  "python_version": null,
  "add_packages": ["requests"],
  "summary": "日志显示缺少 requests，补充该依赖后重新验证。",
  "warnings": [],
  "evidence": ["ModuleNotFoundError: No module named 'requests'"]
}
```

入口、端口、验证路径和安装模式不在补丁允许字段里。程序从已确认方案复制这些字段，再合并经过检查的新依赖。

## 合并和准入是两道检查

`_merge_repair_patch` 检查补丁字段集合、类型、长度和支持的 Python 版本，并从旧方案构造合并结果。后面的校验还要检查依赖名称是否合法，以及新依赖是否有缺模块证据支持。

这个区分很重要：合并函数能保留旧字段，不代表任意字符串已经被批准安装。需要从补丁进入、合并、校验到执行的整个路径看约束。

目前一次补丁最多加入三个依赖，修复最多尝试两次。达到上限后，需要保留日志并交回用户判断，避免不断构建却没有明确进展。

## 这次验收怎样结束

```text
缺少 requests 的真实镜像
 → 启动失败并取得日志
 → 检索诊断案例
 → 真实模型提出窄补丁
 → 校验并重新构建
 → /health 返回 200，JSON 内容探针通过
 → 清理验收容器，保留记录
```

验收文档记录，这次修复的模型请求耗时 2439 毫秒、服务端报告 2170 个 Token。它只对应这一次请求，不能理解为完整部署耗时或账号总账单。

## 遇到打包声明错误怎么办

另一次目标仓库尝试出现 `Multiple top-level packages discovered in a flat-layout`。这类错误涉及目标项目的打包发现配置，补一个依赖并不能解决。

这个错误需要修改项目的打包声明，超出了当前补丁范围，所以这次部署失败。
