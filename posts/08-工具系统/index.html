    学习笔记 08｜工具系统：注册中心 + 执行引擎 + MCP 接入¶

    日期：2026-07-18 标签：AI Agent · 工具系统 · MCP

    物流系统、仓储系统、第三方查询，都等着往 Agent 手里递。第 2 章那五个 @tool 写死的工具，每接一个外部系统就得改代码、重启服务、写一层适配，这条路走不远。这一章把工具层升级成即插即用的生态：内置工具靠注册、外部工具靠 MCP 现问现拿，全部门工具过一条统一管道。

    一、工具系统全貌：内置 + 外部 + 一层统管¶

    主力 Agent 不关心工具打哪来，它只想拿到一份「现在能调哪些工具」的清单：

    • 内置工具：第 2 章那批 @tool 函数，活在自己代码库里，查自己的库或模拟数据
    • 外部工具：物流、仓储、第三方各自把能力包成一个 MCP Server，连过去把工具接过来用

    工具变多就得管理，两层策略： 1. 动态发现与注册：内置工具服务启动时登记；外部 MCP 工具连上 Server 现问现拿（问它有哪些工具、各要什么参数），说明书注册进同一份清单 2. 统一注册管理 + 执行引擎：不管工具从哪来，都走同一套契约校验、权限控制、超时、重试、结果格式化、审计

    二、MCP：外部工具靠什么做到即插即用¶

    MCP（Model Context Protocol）对 AI 工具的意义，就像 USB 对外设：把「AI 应用怎么跟外部工具对接」统一成一套开放标准。工具提供方把能力包成 MCP Server，我们按同一标准做 MCP Client 连过去，不必为每一家单独写适配。

    • Server：工具提供方，对外声明自己有哪些工具、每个叫什么、干什么用、要哪些参数。内部怎么查库是它自己的事
    • Client：工具使用方（客服系统），连上 Server 把声明的工具接过来用

    即插即用的关窍：Client 连上 Server 时先问「你都有哪些工具」，Server 回每份说明书——工具名、用途描述、一份 JSON Schema 写的参数说明：

    {
  "name": "query_logistics",
  "description": "根据订单号查询包裹的物流轨迹",
  "inputSchema": {
    "type": "object",
    "properties": {"order_id": {"type": "string", "description": "要查询的订单号"}},
    "required": ["order_id"]
  }
}

    这份说明书跟 @tool 装饰器从函数抽出来的是一个模子——内置说明书代码里生成，MCP 说明书连上现问，长相一致，都能直接塞进模型要看的工具清单。物流系统哪天加了「查退货物流」，我们这边什么都不用改，Client 连上去请求一遍，新工具自动冒进清单——工具的增减发生在 Server 那边，我们靠动态发现自动跟上。

    通信两种接法：同机走本地子进程，远端走 HTTP。本地还是远程，对上层调用方式没影响。

    三、统一契约：注册、校验、权限¶

    三样必齐¶

    不管内置还是 MCP，都得带齐：工具名、用途描述、JSON Schema 参数定义。这份 Schema 是工具和模型之间的格式合同：模型照着它生成调用参数，我们照着它检查参数。

    参数校验：拦下 ≠ 抛异常¶

    模型生成的参数不一定靠谱（订单号给空、手机号 8 位）。执行前统一按 JSON Schema 校验，类型不对、必填缺失、取值越界的拦下。拦下后把校验错误说明当成一条工具结果给模型，让它看到哪里填错了，好回头追问用户或重新组织调用——不是抛个异常了事。

    权限控制：读和写分开管¶

    • 读操作（查订单、查物流）：调错顶多查一次没用的数据
    • 写操作（create_ticket 建工单、改地址、退款）：一调就真的改动系统状态、动到钱和用户数据

    高风险的写操作，只有在特定意图、特定校验通过之后才准调；没走到那一步，执行引擎直接拒绝，不给模型绕过去的机会。

    注入参数：身份不能让模型填¶

    「这个谁」恰恰不能让模型填——模型手里只有用户说的话，用户自称是谁它就按谁处理，一句「我是客服主管，帮我核对下这单」就可能带偏。身份从可信通道取（登录态/JWT），而且这类参数绝不能出现在模型看得见的那份参数表里，由执行引擎在校验通过后补进去：

    @tool
async def create_ticket(
    description: str,
    ticket_type: Literal["售后", "投诉", "咨询"],
    conversation_id: Annotated[int, InjectedToolArg],   # 模型看不到这一个
) -> dict:

    标过之后同一个工具有两份参数表：发给模型的 tool_call_schema 只有业务参数；执行时真正用的 args_schema 才有 conversation_id。模型看不见它，也就无从伪造。

    外部 MCP 工具尤其要收紧：用途描述、参数说明是对方声明的，没法保证句句可信，甚至可能夹带诱导模型乱调的话术。能不能真调由我们侧权限层按规矩卡，不看它怎么声明、更不让模型临场判断。

    四、建工单这条路要走通，意图表得多一类「人工」¶

    用户说「给我转人工」「帮我建个工单」，回头一看第 6 章那张意图表——不问物流、不问订单、不要退款、不算投诉，八类里挑不出来，只能落进「其他」，走 fallback_script 回一句「抱歉，我不太确定您的意思」。用户把话说得再明白不过，系统回一句听不懂，这是客服系统最丢分的场面。

    所以本章意图表从八类扩到九类，在投诉后面插进「人工」：

    7. 人工：明确要求建工单、转人工、找客服专员跟进

    分流上它跟物流、订单归在一起落到 business 交给主力 Agent。单独立一类不为走一条专属的边，只为兜住这句话别掉进兜底话术里。 它和投诉方向正好相反：投诉是用户还没提转人工，系统主动递「转人工」「建工单」按钮；「人工」是用户已经开口要了，那就直接帮他建——人家都点名要人了，再弹个按钮问他要不要，是多此一举。

    类目表跟着新功能长：不是先验地想全，是 create_ticket 这个能力做出来了，才发现原来的表兜不住通往它的那句话。

    五、统一执行引擎：一套规矩管到底¶

    工具来自内置和外部好几个来源，数量往上涨，外部 MCP 每次调用还要跨网络打到别人家 Server。再让每个工具各管各的容错，重复又容易漏。统一执行引擎 = 所有工具调用从同一个地方过一遍：

    1. 超时第一道：每次调用套上限。本地内置偶尔卡，跨网络外部工具卡的概率更高。超过上限掐断，照样包成失败结果给模型，让它调整策略或向用户交代，不是干耗着
    2. 重试要拿捏分寸：只留给「再试一次可能就好」的暂时性故障（网络抖动、Server 重启）。业务空结果不重试——订单号不存在，查一百遍还是不存在。写操作默认不自动重试：超时未必是没执行成功，也可能只是返回丢在路上，闷头重试就重复改一次、重复退一笔。外部 MCP 写操作更是如此，摸不清对方幂等语义，宁可不重试
    3. 错误三类分诊：参数不合法（校验关拦下回灌）；查询落空（返回「未查到」让模型周旋）；真故障（捕获包成「工具暂时不可用」）。共同点：坏消息如实告诉模型，让它做出应对策略
    4. 结果格式化：外部工具返回五花八门。只挑回答用得上的字段（省 token 也挡敏感字段外泄）、内部枚举码翻成人话（IN_TRANSIT → 「运输中」）、序列化 JSON 中文不转义
    5. 审计日志最后一道：每次调用留痕——什么时候、调了哪个、参数、返回、耗时、成功失败。内置要记，外部 MCP 更要记：调用外部工具等于在别人系统上触发动作，事后追责复盘全靠这份留痕

    六、主力 Agent 把业务 MCP 当工具调¶

    对主力 Agent 来说，业务 MCP 工具和内置 @tool 工具用起来没有分别——两者说明书一个格式，外部工具经 MCP Client 接进来后被适配成跟内置一样的 LangChain 工具对象，一起进工具清单：

    from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "logistics": {"url": "http://logistics-mcp:8000/mcp", "transport": "http"},
    "aftersale": {"url": "http://aftersale-mcp:8000/mcp", "transport": "http"},
})
mcp_tools = await client.get_tools()      # 外部工具，适配成 LangChain 工具

tools = builtin_tools + mcp_tools         # 跟内置合成一份清单
llm_with_tools = llm.bind_tools(tools)

    get_tools() 干的正是动态发现。从这行往后，主力 Agent 眼里只剩「一份工具清单」，调用方式一模一样。加一个业务 MCP Server，清单里就多出几件工具。

    七、工具一多就调不准：Skill 把用法打包起来¶

    清单几十上百件全摆到模型跟前，它开始犯迷糊，三种样子：该调的没调（凭记忆编）、调了不该调的（问物流顺手点退款）、顺序拧了（没拿到订单号就查物流）。

    Anthropic 的「Skill」机制治这个：一个 Skill 就是一个文件夹（SKILL.md 写 YAML 头自我介绍 + 正文 SOP、scripts/ 放干活脚本、references/ 参考资料），平时模型眼前只有每句简短自我介绍，看当前意图跟哪个对得上，才把那个的完整规程和脚本加载进来——这套「用到才展开」叫渐进式披露。前面三种毛病就有救：面前一次只摆当下用得上的几件工具；SOP 把先做哪步、再做哪步写得清清楚楚，模型照着走。

    FC、MCP、Skill 拼成一张生态地图：Function Calling 垫在最底（工具调用的原子，谁都绕不开）；Skill 接手「工具太多怎么挑」（用法打包、按需加载）；MCP 接手「工具在外面怎么接」（标准外部形态、即插即用）。三者还常常你中有我：一个打包好的 Skill 可以再封装成 MCP Server 摆出去，一个 Skill 干活时内部也可以去调 MCP 接来的工具。

    八、代码走读要点¶

    ToolSpec：核心数据结构¶

    一个工具的所有信息收在一处，分成两半： - 前三个字段模型看得见：名字、用途描述、参数定义（缺一样模型就用不好） - 后面全是我们侧策略：能不能调（permission）、超时多久、重试几次、哪些参数注入、结果要不要翻译

    _json_schema_of 的坑：内置工具转的是 tool_call_schema 而不是 args_schema——InjectedToolArg 标记的参数留在 args_schema 但不进 tool_call_schema，校验用这份、给模型看也是这份，注入参数从头到尾不出现在模型视野里。

    导入即注册¶

    每个 builtin 模块底部 registry.register(...)，模块被 import 就完成注册；启动时 pkgutil 扫包逐个 import。好处是加工具成本降到最低：往 builtin/ 丢一个文件就行，不用去中心清单加一行（中心清单写着写着就与实际对不上）。try/except 保护：一个坏文件只跳过自己并记日志，别的照常注册——没有这道保护，一个坏文件让整个工具系统起不来，症状「所有工具都没了」跟真正病因隔着十万八千里。

    get_all_specs：内置先进表、MCP 再来、重名内置优先——外部 Server 不受我们控制，随时可能上线一个跟内置重名的东西，不能让它顶掉我们自己的实现。每轮对话都重新拉 MCP 清单（Server 加工具不用重启就能看到），代价是每轮多一次网络往返，超时封顶就变得很重要。

    执行引擎：never-raises 契约¶

    """管道:查工具 → JSON Schema 校验 → 权限门 → 执行(超时/重试)→ 分诊 → 格式化 + 审计。
坏消息如实回灌模型;审计写失败只 log,绝不反拦工具执行。"""

    never-raises：不管哪一步出问题，都返回一个 ToolRun，坏消息包成 ToolMessage 交回给模型。这个函数跑在 ReAct 环里，抛一个异常整轮对话就断了、用户看到接口 500；而把「参数错了」「工具超时了」如实告诉模型，它完全有能力自己处理。

    • best_match 挑最贴切那条错误：一次校验可能报十几条，全甩给模型它反而不知道该改哪个。回灌语那半句「缺少的信息请先向用户追问，不要编造」是必需的——不写这句，模型十有八九自己编一个值重试
    • 权限门：confirmed 令牌的关键性质是它是函数参数、不是消息内容，只有 agent_tools 在 interrupt 拿到用户确认后才传 True。模型能控制的只有 tool_call 里的参数，没有任何办法把 confirmed 变成真——这是 prompt 约束和代码约束的差别：写在 system 里的「建工单前要征得同意」是一句劝告，模型可以不听；这道门是代码，模型绕不过去
    • 注入时机必须在校验之后：模型看不到 user_id 也可以硬填一个进 args。注入放校验后，我们直接盖掉它填的；放校验前，模型填的值先过校验，格式合法就被当成合法输入
    • 写操作恒不重试；_TRANSIENT 只有四类：超时 + 网络抖动（TimeoutError/ConnectionError/httpx.TransportError）。业务异常不在列。query_faq 设重试 0——底下是整条 RAG 管线，超时多半是上游真慢，重试纯粹烧时间
    • 分诊界线：查不到东西不是故障。用户报个不存在的订单号，工具正常返回「没找到」，走成功路径，由返回值表达语义；只有工具真的挂了才进分诊。两件事混在一起，模型就分不清「确实没有这单」和「系统坏了」
    • 格式化三层剥：MCP 工具经 adapters 回来是内容块列表 → 拆文本 → JSON 解 dict → format_result 钩子挑字段翻人话。钩子外面包 try：格式化是扩展点，钩子炸了就降级透传原始结果——工具明明调成功了，不能因为一个美化步骤把它报成失败
    • 审计：五种结局全记，包括被校验拦下和被权限拒绝的——这两类恰恰最该复盘（模型总在某个工具上填错参数说明描述不清楚；写操作频繁被拒说明确认流设计有问题）。不挂外键：审计要记的可能是一次没有会话上下文的调用或会话已清理，外键一拦这条审计就写不进去。几处截断（tool_name 是模型给的可以编几千字、error_message 可能内嵌超长参数值）也是为「一次插入失败不丢整条审计」服务。审计失败只 log 不反拦——工具已执行完，因为记不下来就报错是本末倒置

    MCP 接入¶

    fetch_mcp_specs 两处保护各治一种失败模式： - except 治「Server 挂了」：单台不可达跳过它的工具，本轮照常进行，模型手上少几个工具——工具少一个是降级，整轮崩掉是故障，差着量级 - asyncio.wait_for 治「Server 假死」：进程还在、TCP 握手成，就是不回数据，except 等不到触发，只能靠超时。清单每轮现拉，延迟直接加在用户等待上，必须封死 - handle_tool_errors=False：让工具错误原样抛出来交执行引擎分诊。默认 True 会由 adapters 吞掉包装成消息，格式跟我们的回灌语不一致，审计也记不到真实异常类型 - 结果翻译登记我们侧：Server 返回内部枚举码 IN_TRANSIT、用不上的承运商编码，不翻译模型会原样写进给用户的回答。权限/格式化只认我们侧，Server 自报用途描述仅供模型参考——把这两件事交出去，等于把系统安全边界交给一个不受自己控制的进程

    工单确认流¶

    if ticket_calls and tspec is not None \
        and engine.validate_args(tspec, dict(ticket_calls[0].get("args") or {})) is None:
    first_args = ticket_calls[0]["args"]
    decision = interrupt({"type": "confirm_ticket",
                          "preview": {"ticket_type": first_args.get("ticket_type", "咨询"),
                                      "description": first_args.get("description", "")}})
    • 先纯校验，参数齐才 interrupt：参数不齐就弹卡，用户看着空描述预览点确认，工具照样因参数不全失败，白弹一次还让用户觉得系统很傻。参数不齐走引擎「校验拦下」回灌，模型收到「缺少 description」自然向用户追问，卡片压根不弹
    • validate_args 被复用：注册中心校验规则和「要不要弹卡」用同一份判据，不会出现引擎认为参数不全、节点认为够的分歧
    • 守着第 6 章纪律：interrupt 之前只有查清单和跑校验，纯计算，resume 重跑无副作用
    • 模型偶尔一轮申请两次建工单：只处理第一个，其余回「一次只处理一个建工单请求，本次调用已忽略」。不处理直接丢掉的话，那个 tool_call 没有对应的 ToolMessage，消息序列不完整，下次调用报错

    九、实战要点¶

    功能需求七条：① 注册中心（内置启动登记、MCP 现问现拿、新工具注册即用不改核心代码不重启）；② 参数校验（统一 JSON Schema、错误回灌不抛异常）；③ 权限控制（写操作只有 create_ticket、执行引擎把门、没确认直接拒、外部 MCP 权限只认我们侧）；④ 执行引擎（统一超时/重试/错误处理/结果格式化，写操作默认不自动重试，三类分诊）；⑤ 审计留痕（tool_audit_logs 每次调用落一条含被拒被拦的、不挂外键、失败不反拦）；⑥ MCP 接入（自建物流/售后两台业务 Server 独立进程 Streamable HTTP，query_logistics 从内置清单下线）；⑦ 建工单确认流（Agent 先核对信息缺必填追问、interrupt 推预览卡、确认 resume 放行落 tickets、取消按权限拒绝落审计）。

    验收六条：① 新写一个简单工具只注册不动核心代码 Agent 就能用；② 两个 MCP Server 单独起进程问物流轨迹 Agent 都通过 MCP 查到数据回答；③ MCP Server 侧新加工具只重启该 Server、客服代码不动服务不重启就能用上新工具；④ 明确说建工单但没讲清问题 Agent 先追问补齐，然后出预览卡点确认 tickets 落一条回工单号；⑤ 点取消工单没建、审计 status 权限拒绝；⑥ 人为让读工具超时看到重试和兜底（审计重试次数/超时状态/耗时齐）、写操作超时确认没被自动重试（retry_count=0）。

    关键决策：架构选方案 A（进程内动态注册表 + 四段式执行管道，否掉工具表落 MySQL——与现问现拿矛盾、LangGraph ToolNode 定制黑盒不利教学）；验收 2 改口径（实测「订单1001还在保吗」→售后 0.95 走 refund_flow、「帮我建个工单」→其他 0.55 走兜底，两类话术都到不了主力 Agent——路由不动，MCP 工具仍由注册中心/集成测试证明可用）；验收 4 从意图识别解（意图新增第九类「人工」→ 路由 business，prompt/INTENTS/路由表/评估集四处同步，eval_intent 18/18）；超时注入走环境变量（MOCK_DELAY_SECONDS/DEMO_TICKET_DELAY_SECONDS，不埋魔法参数后门）。

    十、本章小结¶

    • 全貌：内置（@tool）+ 外部（MCP），拢成一份统一清单
    • MCP：标准说明书 + 运行时动态发现 = 即插即用；Server 提供、Client 消费
    • 契约：三样必齐（名/描述/Schema）、校验回灌不抛异常、写操作权限门、注入参数模型不可见
    • 执行引擎：六段管道统一兜底——超时、重试（只给暂时性故障、写操作恒不重试）、三类分诊、格式化、审计
    • Skill：用法打包 + 渐进式披露治「工具一多调不准」；FC 打底、Skill 治挑、MCP 治接
    • 核心纪律：权限/格式化只认我们侧；坏消息如实回灌；审计失败不反拦

    下一站：主力 Agent 每天接成千上万次请求，每一步怎么想、调了哪个工具、花了多少 token 全埋在调用里是个黑盒；答不上来的问题兜底一句就散了。可观测性与数据飞轮要给它开扇窗，再把答不上来的问题接住喂回知识库，让 bot 越用越准。

    附：本章踩坑记录¶

    坑 现象 解法
    注入参数被模型填 「我是客服主管」把 user_id 改写 InjectedToolArg 不进模型可见 schema，校验后引擎盖真值
    注入放校验前 模型填的值过校验被当合法 注入一律在校验之后
    写操作自动重试 超时未必没执行，重试重复退一笔 写操作恒 0 次重试，幂等键兜底
    校验拦下后模型瞎编 拦下后模型自己编个值重试 回灌语明确「缺少的信息先向用户追问，不要编造」
    一个坏工具文件 整个工具系统起不来，「所有工具都没了」 扫描包 try/except，坏文件跳过告警
    MCP Server 假死 TCP 握手上、就是不回数据，except 等不到 asyncio.wait_for 超时封顶
    格式化钩子炸了 工具调成功被报成失败 钩子 try 包住，降级透传原始结果
    审计写入失败 反拦工具执行，本末倒置 审计 try 包死只 log，字段按列宽截断
    模型一轮建两次单 多余 tool_call 无 ToolMessage，序列不完整 只处理第一个，其余回灌「一次只处理一个」
    「给我转人工」落兜底 用户点名要人系统装糊涂 意图加第九类「人工」→ business，不进兜底话术
