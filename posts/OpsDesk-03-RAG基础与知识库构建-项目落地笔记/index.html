    第 03 章：RAG 基础，跑通全链路 —— 项目落地笔记¶

    日期：2026-08-19 标签：AI Agent · OpsDesk · 项目落地笔记

    涉及源码：app/kb/chunking.py、app/kb/documents.py、app/kb/milvus_client.py、app/core/retrieval.py 涉及数据：data/kb/（6 份运维文档）、scripts/build_kb.py、scripts/vectorize_kb.py

    这一章我搭了什么¶

    把运维知识从"模型的记忆"搬到"外部知识库"，让系统能回答知识类问题（电机过热怎么排查、停送电规程、P1/P2/P3 响应时效）。

    两条线：入库（文档 → 切块 → 向量化 → 存 Milvus）和在线（问题 → 检索 → 证据拼 Prompt → 严格按证据回答、标来源编号）。

    知识库素材是我在运维岗位上实际整理的 6 份文档：设备台账、运维 FAQ、故障排查手册、工单制度、服务等级承诺、安全规程。最后切出 37 块入 Milvus。

    遇到的问题¶

    1. 中文没有词边界，按英文分隔符切会切烂¶

    现象：直接套英文的切分器，中文句子被切得支离破碎。

    解决：中文分隔符换成中文优先的顺序——["\n\n", "\n", "。", "！", "？", "；", "!", "?", ";", "，", " ", ""]，段落优先、再句末标点、再逗号、最后逐字兜底。

    2. 按长度硬切，把安全规程从中间切两半¶

    现象：这是整个 RAG 里最危险的坑。一条安全规程从中间被切开，检索只命中前半句"停电、验电、挂牌上锁三步"，后半句"严禁断电即开盖（母线电容仍带电）"落到别的块里，模型就敢答"断完电直接开盖检查"——这种回答是要出人命的。

    解决：切分不看长度，顺着标题层级切（MarkdownHeaderTextSplitter，按 # ~ #### 的标题拆），每块带着自己的标题路径（如「常见故障排查手册 / 电机过热报警怎么排查」）；表格按行切、每块重贴表头。

    教训：RAG 的质量上限在切分，切分保不住语义完整性，后面检索、生成做得再好都白搭。

    3. 块与块之间丢上下文¶

    现象：一个主题被切到相邻两块，用户问的问题证据落在上一块的结尾，检索只捞到下一块开头，答不完整。

    解决：加了句子级重叠——apply_sentence_overlap，切完的相邻两块之间，把上一块结尾的若干完整句补到下一块开头（单句超长就整句保留，优先"不留半截话"）。

    4. 一句话问两件事，向量被主语义带跑¶

    现象：用户问「3号线的电机过热报警了怎么排查,顺便问下备件散热风扇有没有货」，整句去检索时向量被主语义带跑，只有一个意图能挤进前排。

    解决：检索前先按标点拆子句（split_clauses），两个意图各查一遍，再轮转合并（每个子句轮流出一条，按 chunk id 和 section 去重）。

    教训：这招有个前提——必须配精排才有意义。评估集实测：拆句+重排 +0.02，其余三路 -0.04 到 -0.06（没有精排的单路检索拆完反而更吵）。方法不是越多越好，要看成不成一套。

    5. 长证据被塞进中段，模型记不住两头¶

    现象：检索回来的证据直接拼进 Prompt，结果最相关的排在中间，模型对中间的注意力反而弱（lost-in-the-middle 效应）。

    解决：arrange_head_tail——最相关放首、次相关放尾，其余按序居中，缓解注意力衰减。

    6. 怎么知道哪些块是"关键条款"¶

    现象：后面做置信度闸和审核打标时，需要知道检索回来的证据里有没有关键条款（时效、费用、安全这类）。

    解决：入库时打标——KEY_TERMS = ("报修","工单","故障","时效","巡检","维保","备件","安全","合同","设备")，标题+正文开头命中词表就标 is_key_clause=1。这个标后面几章（置信度信号、飞轮审核打标）一直复用，所以导出公共名 KEY_TERMS / is_key，不各写各的。

    学到的一课¶

    • 切分决定 RAG 天花板：结构感知切分 + 标题路径 + 表格重贴表头 + 句子级重叠，每一层都是踩坑换来的
    • 检索不是越多越好：拆子句要配精排，混策略要配重排，方法之间是配套关系不是叠加关系
    • 中文处理要单独想：词边界、标点、分隔符全都要针对中文调整
    • 打标要早：入库时把"关键条款"这种标打上，后面所有模块都能复用，别到用时再回捞

    怎么验证¶

    # 建库 + 向量化 + 预览
make kb-build
make kb-vectorize
make kb-preview

# 起应用后问知识类问题，看是否严格按证据回答并标来源编号：
# {"user_id":"u1","message":"电机过热报警怎么排查"}
    基础 RAG 到这里能答了。但检索质量还很糙——纯向量漏字面词（设备型号差一位就是另一台），纯关键词换说法就查不到。下一步就是把这两路各补各的盲区、再用精排把噪声压下去。
