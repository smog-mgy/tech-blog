    第 02 章：Function Calling 工具链 —— 项目落地笔记¶

    日期：2026-08-15 标签：AI Agent · OpsDesk · 项目落地笔记

    涉及源码：app/tools/registry.py、app/tools/engine.py、app/tools/business.py、app/tools/builtin/

    这一章我搭了什么¶

    让系统从"会聊天"变成"能干活"。搭了一个工具注册中心（内置工具和 MCP 工具统一登记成 ToolSpec，三样必齐：工具名、用途描述、JSON Schema 参数定义）和一个统一执行引擎（所有工具调用的唯一通道）。

    最核心的认知转变：模型只决策，框架来执行。模型输出的是"调用意图"（工具名 + 参数），真正的执行、校验、权限、错误处理全在框架侧。用户说「VFD-3005 变频器过载报警帮我报修」，模型只是吐出 {"name": "create_ticket", "arguments": {...}}，接下来框架查注册表 → 校验参数 → 过权限门 → 执行 → 结果回填，才轮得到模型组织语言。

    遇到的问题¶

    1. 工具权限该听谁的？—— 外部 Server 不可信¶

    现象：接了 MCP 工具后，担心外部 Server 自报"我是只读工具"就放行，会被带节奏。

    解决：权限我们侧独裁。WRITE_TOOLS = {"create_ticket"}，写操作只有建单这一个，按名字定；未登记（含所有 MCP 工具）一律按只读放行。外部 Server 的描述只能给模型参考，能不能调、权限归谁由代码说了算。

    2. 身份如果让模型填，归属校验就废了¶

    现象：早期想让模型在调工具时带上 user_id，后来发现这是死路——模型凭什么知道"我是谁"？它可以从对话里猜，也可以瞎编。

    解决：ToolSpec 上加 inject_user_id / inject_conversation 标记，执行前由框架从可信通道注入，参数 Schema 里对模型不可见。身份不是模型的输入，是系统注入的上下文。

    3. mock 数据每次都不一样，评估没法做¶

    现象：用 random 生成工单数据，同一张工单每次查结果都不一样，测试和评估根本没法对比。

    解决：改固定随机种子的纯函数——ticket_snapshot 用 random.Random(f"ticket:{ticket_id}")，同一工单号永远返回同一份快照（状态、优先级、故障类型、设备、产线、处理人都是稳定的一整套）。演示单固定为 WO-2026-0001 / WO-2026-0002 两笔，每账号名下都有，报别的号（如 WO-2026-9999）就能演示拦截。

    教训：没有线上系统时，可复现的 mock 比随机的 mock 值钱——它让评估、测试、演示全部稳定。

    4. 归属校验写了多处，早晚有一处漏¶

    现象：最初工具层一套归属判断、节点层又写一套，两边规则还不一样，差点出现"工具层拦了、节点层放行"的洞。

    解决：收成一个唯一判定点 owns_ticket(user_id, ticket_id)，工具和节点全调它，不各判各的。还加了一条铁律：空 user_id 一律不放行——身份是注入进来的，注入没接上就是空串，那种情况放行等于没做校验。

    5. 什么错误都重试，浪费还更糟¶

    现象：工具调用失败就重试，后来发现业务异常（比如工单不存在）重试 N 次还是失败，白白耗时间。

    解决：定义"值得重试"的清单——_TRANSIENT = (asyncio.TimeoutError, TimeoutError, ConnectionError, httpx.TransportError)，只有超时、网络抖动这类暂时性故障才重试；业务异常直接如实回灌给模型，让它修正参数或如实告诉用户，不编造结果。审计写失败只记 log，绝不让可观测反过来卡住业务。

    学到的一课¶

    • 职责边界：模型负责"决定调什么"，框架负责"真正执行"——可靠性问题（校验、权限、超时、重试）全在框架侧解决，不指望模型自觉
    • 安全边界：权限独裁（写操作白名单）、身份注入（模型没资格填）、归属单一判定点（不各判各的）这三件套是工具系统的地基
    • 可复现：固定种子的纯函数 mock，让没有线上数据的系统也能稳定评估
