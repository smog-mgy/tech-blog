    学习笔记 09｜Agent 可观测性与数据飞轮：给黑盒装眼睛，把答不上的问题喂回知识库¶

    日期：2026-07-24 标签：AI Agent · 可观测性 · 数据飞轮

    前面八章把系统造出来了，可它跑起来什么样，我们一直没真正看清过——每一步想了啥、调了哪个工具、花了多少 token，全埋在一次次调用里。上线跑了一周，老板端着两个问题找过来：昨天有个用户收到条离谱回答，到底哪一步出的岔子？这个月 token 花超了，钱到底花哪了？你张了张嘴，答不上来。再往下想一层，那个收到离谱回答的用户，问题兜底一句就散了，下回换个人问同样的事，照样答不上来。这一章办两件事：把黑盒照亮（可观测性），把答不上的问题接住（数据飞轮）。

    一、黑盒里到底看不见什么¶

    用户一句话进来，主力 Agent 在 ReAct 循环里走好几步才收敛出回答。收到离谱回答，可能是某一步检索回了错的资料，也可能是模型拿着对的资料想歪了，还可能是某个工具超时返回空值它硬着头皮往下答——光看最后那句回答，根本分不出是哪一步出的问题。

    token 同理：一次请求每走一步都把新结果追进对话历史再喂给模型，步数越多历史越长烧得越多；一个月成千上万请求，哪类问题最费、费在哪一步，全都看不见。

    两个问题背后是同一件事没做：每一步模型想了什么、调了什么工具带了什么参数、检索回了哪几条、花了多少 token、哪一步慢——这些过程信息在请求跑完那一刻就丢了，没留痕。把这些过程记下来、还原成看得见的东西，就是可观测性要干的事。

    二、调用树：trace 与 span¶

    要记成什么样？答案是记成一棵调用树。

    一次请求就是树的根。主力 Agent 每走一步是树上的一个节点，这一步里调的那次模型、那个工具、那次检索，都作为子节点挂在这一步下面；工具内部又调了别的，再往下长一层。谁调了谁、先后顺序、各花多久，顺着树从上往下看得清清楚楚。业内把这样一棵树叫一条 trace，树上每个节点叫一个 span。

    这棵树的形状跟第 5 章那张 LangGraph 图有异曲同工之妙——图上有指代消解、意图识别、检索、主力 Agent 节点，一次请求流过这几个节点，trace 树上就长出对应几段。当时讲编排层为什么选 LangGraph 留的伏笔「往后配可观测会顺着这张图对齐每个节点」，指的就是这里：图上一个节点，trace 上就长出一段。

    三、接 Langfuse：数据不出门，接入只多挂一行¶

    总不能自己在每个节点手写埋点。本系统选 Langfuse——开源、能装自家服务器。整套选型立场就是数据不出境、能自部署就自部署；课程演示用云端即可，避免本地部署太重。

    接入只两步：设三个环境变量（public/secret key + base_url），再在图编译时挂一次回调：

    from langfuse.langchain import CallbackHandler

langfuse_handler = CallbackHandler()
graph = graph_builder.compile().with_config({"callbacks": [langfuse_handler]})

    就这么多。挂完之后跑图时每次调模型、调工具、检索，Langfuse 自动采集、拼成 trace 树，节点里的业务代码一行不用改。LangGraph 跑图会把每个节点的输入输出往外发信号，Langfuse 顺着信号还原整棵树，包括每个节点的 prompt、返回、token 消耗和耗时。

    另一条路是 LangSmith（LangChain 官方生态，跟 LangGraph 同源）：连回调都不用挂，设两个环境变量就接上。代价是托管服务、链路数据上它的云端、而且花钱。不介意数据出境或只想快速搭原型，走 LangSmith 更省事。

    四、防悄悄退化：自动化评估流水线¶

    trace 一次只照见一棵树，系统整体在不在悄悄变差，单看单条看不出来。客服系统里这事特别容易发生：改了个 prompt、给知识库补了一批知识、把某意图的模型从大换小，改的时候盯着几个例子觉得没问题就上了，可这一改说不定把另一类问题的准确率悄悄带下去一截。靠人肉抽查发现不了，等用户投诉多了才察觉，早晚了。

    治它靠自动化评估流水线：把第 4 章那份评估集和指标（检索段 Recall@K、MRR，生成段 Faithfulness）搬到上线之后，定期自动跑一遍（每天一跑，或每次改动后跑一次），每轮分数落表，连成趋势线。

    重点全在趋势线上——盯的是分数有没有往下掉，不是某一次考了多少分。哪天某个指标的曲线突然拐头向下，报警拉起来，再回头借着 trace 树定位是哪次改动、哪类问题拖垮了它。

    五、Cost Control：按意图算账¶

    trace 树已经把每一步的 token 记下了，缺的只是换维度汇总。把意图识别结果打成 trace 的 tag（intent:xxx），按意图把 token 分堆一算，哪类最烧钱立马现形：

    • 烧钱大头：商品咨询（检索回来的一堆资料全塞进上下文才能作答）、退款退货/售后（子流程步骤多，订单数据、政策条款一样样取回来喂进去），一次请求的 token 比查物流高出一大截
    • 便宜高频：物流、订单，查一次数据就收敛作答

    这张按意图的账正好接上第 6 章「先求准再求省」的思路：物流、订单这类高频又简单、边界又清晰的意图，换小模型甚至干脆不走模型直接返回接口结果，省的量最大又不容易换出错；商品咨询、退款退货、售后必须稳住准确率（答错了要么误导、要么惹出真金白银的纠纷），这几类得留大模型。省了多少、准确率掉没掉，评估流水线盯着。

    六、数据飞轮：答不上的问题不能就这么散了¶

    知识库一开始就不可能完备（第 3 章说过：人工整理和历史对话挖掘两条来源缺一不可）。飞轮转起来，答不上的问题被记录、沉淀、补进库，下次能答了——从用户交互里收集问题、处理后反哺系统的闭环。

    三个入口汇进同一个低置信度问题池：

    入口 谁挡的 看什么
    证据置信度低 检索/精排（零额外模型调用） 精排 Top1 相关性分、有效证据数、Top1-Top2 分差、关键条款命中——量化「这批证据到底符不符合问题」
    生成阶段 useful=false 第 4 章那道生成闸 检索回知识后模型自评「资料够不够答」，不够就拒答+兜底落池
    用户反馈没解决 用户点 👎、继续追问、人工改答 系统觉得能答、用户看完还是没解决

    evidence_confidence 看检索证据强弱，useful 看证据撑不撑得起回答，一个偏检索一个偏生成，不重复。

    进池不等于入库，只是说明这条问题值得被运营看见。

    七、从口语原话到能入库的知识：标准化 + 查重¶

    用户原话「我上周买的那双鞋跑了两次就开胶了这也太坑了吧能不能给我退了啊」，带情绪、带口语、夹着一堆无关碎片，直接入库当 FAQ 既难检索也没法复用。

    第一步问题标准化（Question Canonicalization）：让模型把原话去噪、剥掉情绪口语、只留核心诉求，改写成一句 FAQ 式标准问题（→「商品出现质量问题（如开胶）能否退货」），顺带生成一条示例答案备查。

    第二步查重：同一个知识缺口一百个用户能有一百种问法，全当新问题塞进待审队列，人工审到崩溃。做法是标准化时顺手做：给模型喂一批候选（待审队列里已有的标准问题），判当前这条跟哪个是同一个意图——命中就返回那条的 matched_question_id、合并过去、累加一次出现次数；没命中返回 null，作为新问题入池。

    标准化和查重合成一次模型调用：两件事本来就要看同一份材料，分两次得多喂一遍材料、多花一倍钱。返回结构：

    {
  "normalized_question": "商品出现质量问题（如开胶）能否退货",
  "matched_question_id": 128,
  "ai_suggested_answer": "..."
}

    累加出来的出现次数是宝贵信号：一个缺口被越多用户反复问到，越该优先补。飞轮从来不缺问题，缺的是先补哪个的依据——靠频次排优先级。

    八、进库前的三道闸：不是所有问题都值得沉淀¶

    1. 垃圾过滤：乱输入、测试胡打、不当言论直接丢，压根不是业务问题
    2. 看时效：强时效问题会自然过期（「双十一满减活动今晚几点结束」今天补进库、过两天就是误导），不沉淀，让模型说不知道、转人工
    3. 评频次：低频一次性的冷门问题，不值得占知识库的位置、耗人工精力

    过了闸、人工核准答案，走第 3 章那套落库流程向量化写回知识库。闭环合上：下次语义相近的问题进来，检索直接命中新补的知识。

    九、攒多了得分堆：交给微调分类器¶

    飞轮跑一段时间，池里攒下几千上万条问题。要搞清用户到底最常卡在哪一类（物流/退换货/尺码/开发票），才好定先补哪块的优先级。量小让 LLM 逐条打标能凑合；几万条逐条调大模型又贵又慢，方言语错别字一句话夹好几个诉求还容易打偏。这种海量、类目固定、要便宜要快的归类任务，用微调过的小分类器批量跑——正是下一章的正题，本章点到为止。

    十、代码走读要点¶

    attach_observability：观测是增强，不是依赖¶

    def attach_observability(graph):
    """编译后挂一次 Langfuse 回调,全图自动 trace。
    未配置时原样返回——不挂、不 import langfuse。"""
    if not langfuse_enabled():
        return graph
    _init_client()
    return graph.with_config({"callbacks": [_make_handler()]})

    未配置时连 import langfuse 都不执行——学员不想搭一套 Langfuse，全课照样跑得通，只是少一块面板。配置走 settings 显式传参，不读 os.environ（整个项目的配置口径是 .env + pydantic-settings）。

    run_inline：那个「功能通了不等于全通了」的坑¶

    class _InlineCallbackHandler(CallbackHandler):
    """run_inline=True:让 LangChain 在调用方协程内联执行回调,而不是丢进独立 task。
    没有它,handler 的 OTel context.attach 挂在别的 task 上,节点代码里没有活动
    span 上下文,tag_intent 的 propagate_attributes 写不进当前 trace(实测踩坑)。"""
    run_inline = True

    LangChain 默认把回调丢进独立 task 跑，context.attach 就挂在那个 task 的上下文上；回到节点代码时当前协程没有活动 span 上下文，tag_intent 往 trace 上补属性就写不进去。表面看一切正常：trace 有了、节点有了、耗时有了，只有「按意图打标」这一件事静默失效——不是去用那个功能，根本发现不了。这类框架集成的坑值得记：附加能力得单独验一遍。

    tag_intent：别往可能已 ended 的 span 上写¶

    直觉写法是打开传播上下文然后什么都不做，让属性落到当前活动 span。但 LangGraph 异步调度下那个 span 可能已经 ended，OTel 对已结束 span 的写入是静默丢弃的——不报错、不告警，就是没写进去。解法是在传播上下文里现建一个 event：新 span 必然存活，trace 级 metadata/tags 随它上提到整条 trace。整个函数 try 包住、失败只 warning——观测失败不许影响业务流（本章纪律，代码里出现至少五次）。

    用量收口：一个把成本账放大一个量级的 bug¶

    class _CumulativeUsageChatOpenAI(ChatOpenAI):
    """修正流式用量被重复累加的问题。
    有些 OpenAI 兼容通道在**每个** chunk 上都重报一遍**累计**用量,而 langchain-openai
    把各 chunk 的用量**相加**。两件事凑到一起,一次调用的 token 数会被放大到 chunk 条数倍
    ——实测 24 个 chunk、input 恒为 11,聚合出来是 264。..."""

    两个各自合理的设计凑在一起就出事：上游每个 chunk 重报累计用量（客户端随时断开也能拿到当前用量，说得通）；langchain-openai 把各 chunk 用量相加（规范通道只在末尾报一次，相加正好等于总量，也说得通）。凑一起 24 个 chunk 就把 11 个 input token 累成 264。

    后果两处：本章成本统计整体虚高一个量级；更隐蔽的是第 5 章 ReAct 那道 token 预算闸被虚高数字第一步就顶穿，should_continue 直接返回停止——表面症状「模型不爱调工具」，谁会想到是用量统计的问题。stream_usage=False 还关不掉（那个开关只管要不要主动请求，上游照发、库照加）。

    修法：_convert_chunk_to_generation_chunk 入口把累计值换成相对上一个 chunk 的增量（_diff_usage 递归处理嵌套的 *_details，只改外层会让明细对不上总数）。「任何一项变小就清零基准」是自愈信号：同一实例被复用、结构化输出的链多次 invoke 时，第二条流的第一个 chunk 用量突然变小，认出信号清零基准，否则算成负数被 max(0,...) 抹成 0。

    证据置信度：四个信号，零额外模型调用¶

    top1_score     精排 Top1 的 rerank_score
valid_count    有效证据数:rerank_score >= VALID_SCORE_FLOOR 的条数
margin         Top1 - Top2 分差;单条时取 top1 自身
key_clause_hit Top3 文本是否命中关键条款词表(复用 ch03 入库同款 KEY_TERMS)

    比第 4 章那道只看 Top1 的机械闸升级成四信号加权（0.5/0.2/0.2/0.1）。「零额外模型调用」是这套设计的前提——全部来自已算出的检索/精排结果，这道闸不额外花钱、不加延迟；要是需要再调一次模型，就该重新掂量值不值。权重是模块常量不进 settings（模块 docstring 写明：评估集校准的是阈值不是权重，两层都可调的话调的人就不知道该动哪个，两个旋钮互相干扰说不清效果归谁）。返回值带四个原始信号——落池 reason 和 trace 留痕都要用，光留总分，看到「0.28 判弱」根本说不清是哪项拖的后腿。

    阈值不拍脑袋：拿 ch04 评估集，A/B/C 桶（应可答）与 D 桶（应拒答）分别算置信度分布，扫阈值取 Youden J（=可答通过率 - 应拒放行率） 最大的分离点——同时惩罚两类错误：定高了误拦真能答的，定低了误放本该拒答的。脚本给推荐值、人工回填 settings，不自动改配置（这数字影响线上拒答率，值得有人看一眼再决定）。

    召回快照：三态语义¶

    walked_retrieval = bool(state.get("fallback_source"))
snapshot = state.get("retrieved_snapshot") or ([] if walked_retrieval else None)

    走了检索且有召回 = 列表；走了检索但零命中 = []（审核页显示「已检索,零命中」，这是"真缺知识"的强信号）；压根没走检索 = NULL。空列表和 NULL 不能混——用同一个值表示两种情况，审核的人没法排优先级。

    反馈快照回捞¶

    👍 只记日志（答对了是应该的，落库也推不出下一步动作）；👎 才有信息量。点踩时从 checkpointer 读该会话终态把召回快照捞回来，关键在 _same_question 那道比对——用户点的可能是好几轮之前的消息，checkpointer 存的是最近一轮快照，对不上就不塞：宁可没有快照，也不能把别轮的召回结果安到这个问题上，那会把审核的人带到沟里。回捞失败照常落池——快照是锦上添花，问题原话才是必须留下的东西（纪律第三次出现）。

    飞轮流水线：四条语义¶

    批处理语义:
- 游标 = matched_review_id IS NULL,处理完回写,天然幂等可重跑;
- 串行逐条:同批同义问题第二条能命中第一条刚建的行,不重复建缺口;
- 命中任何状态的候选都只累加 occurrence_count(驳回即终审,不复活);
- 解析失败/幻觉 id:该条跳过并告警,游标留在原地下轮重试。
    • 游标是「有没有回写归并落点」，不是时间戳——处理完回写，中途挂掉重跑时已处理的自然被过滤，天然幂等
    • 串行逐条是刻意的：同批五条「运费怎么算」的口语变体，第一条建缺口、后面四条要能命中它；并发跑四条互相看不见，建出五个重复缺口。落点：process_pending 每条都重新拉一遍候选（limit=201——多拉一条判断是否真被截断，恰好 200 条候选时不会误报截断）
    • 驳回即终审是业务判断：被人工驳回过说明不该进库，之后再出现同类只累加计数，不重新变回待审——不然被驳回的问题反复冒出来烦人
    • 幻觉 id 校验：matched_question_id 必须在候选里真实存在。结构化输出最典型的一类幻觉：schema 约束了字段是整数，但约束不了是有效 id。不验一道就累加，那次计数加到别的问题身上。截断时日志明说「查重覆盖不全」——降级必须说出来，不然报告上「新建 12 个缺口」，看的人以为查重完整

    review_queue 表：一行一个去重缺口（normalized_question/ai_suggested_answer/occurrence_count/review_status/approved_answer），id 就是查重返回的 matched_question_id，两处是同一个东西。低置信池加 matched_review_id（飞轮游标）+ retrieved_chunks（审核材料）两列。

    审核写回：整体回滚¶

    chunk_ids = await _write_chunks([chunk])
await _vectorize()

    写库成了、向量化挂了，pending 行留在库里——第 3 章讲过 vectorize_pending 处理全部 pending，下次谁触发都会处理掉这条残留；而这次审核报了错状态还是待审，人会再点一次通过，于是又插入一条一模一样的知识。解法是整体回滚删掉本次插入的行；回滚本身失败就记「需人工清理」的日志留线索。

    末尾的并发窗口：知识库已写入但待审状态被另一个人先改，不能装作成功——如实报 409，错误信息写清「知识已写入，请人工核对」而不是让人简单重试。

    账算给谁看¶

    Cost Control 不自己埋点，直接查 Langfuse Metrics API，按 intent:xxx tag 分组。所以那个 run_inline 静默失效的坑要是没修，这份报告出来是一片空白，还看不出哪里错了。产物落成 JSON，前端「观测与成本」页只读这份，不另算一份——避免页面和报告两个数对不上。自定义模型名在 Langfuse 无内置单价，脚本只统计 token 数不硬算金额（要看钱去界面配单价）——一个统计脚本自己编一套价格表，用的人迟早拿着它去跟财务对账。

    十一、实战要点¶

    功能需求六条：① 接 Langfuse（环境变量 + 编译时挂一次回调，trace 树可铺开看）；② Cost Control（意图识别结果打进 trace 元数据，按意图统计 token）；③ 数据飞轮三个入口（证据置信度升级成正式置信度检查、四信号加权、阈值拿评估集校准不拍脑袋；生成阶段 useful=false 确认接进飞轮；👎 前端反馈接到后端落池）落池时存召回片段快照，👎 从该会话当轮尽力回捞，那轮真没走检索才空着；④ 飞轮流水线（标准化 + 查重合并累加次数 + review_queue 待审队列，人工审核通过走 ch03 落库写回知识库）；⑤ 自动化评估流水线（复用 ch04 评估集定期跑，分数落 eval_runs 表连成趋势）；⑥ 前端后台审核页（列出标准化问题/出现次数/示例答案，能通过/驳回，详情看到归并原话和召回片段）。

    验收六条：① Langfuse 里能点开任意一条请求看完整链路；② 问知识库没有的问题 → 兜底话术 + 出现在待审队列，点开看到原话和召回片段；③ 审核页点通过后，同一个问题再问就能答对——飞轮转完一整圈；④ 聊天页对回答点 👎，问题落池、标准化查重后出现在待审队列；⑤ 能拿出按意图汇总的 token 花销，哪类最烧钱看得出来；⑥ 评估流水线至少跑两轮，能看到指标趋势对比。

    本章不做：低置信度问题按主题归类的微调分类器（下一章）。

    十二、本章小结¶

    • 可观测性：过程信息留痕 → trace 树；Langfuse 编译时挂一次回调零侵入，数据不出门；LangSmith 省事但上云
    • 防退化：评估集定期回归 + 趋势线，报警后借 trace 定位
    • 成本：意图打成 tag 按意图分堆，简单意图可换小模型，复杂意图保准确率
    • 数据飞轮：三个入口 → 低置信池 → 标准化 + 查重（合成一次调用、频次排优先级）→ 三道闸人工审核 → 写回知识库
    • 核心纪律：观测和飞轮都是旁路，任何一处失败都不许影响业务流（代码里至少五次）
    • 两个静默失效的坑：run_inline（属性写不进 trace）、OTel 对 ended span 静默丢弃——功能通了不等于全通了

    下一章换方向：前面所有改进都在系统这一侧，模型本身一直是拿来即用。现在轮到它了——把飞轮攒下的问题按主题归类的小分类器亲手训出来。
