    OpsDesk 10｜旁路分类器与微调 · 项目复盘¶

    记录日期：2026-09-17 标签：AI Agent · OpsDesk · 项目落地笔记

    说明旁路主题分类器的用途，阅读仓库中的留出集报告，同时保留小样本评估的限制。

    涉及脚本：scripts/ch10/（build_corpus / prelabel / build_dataset / train / evaluate / export_onnx / serve / classify_pool / validate_golden / scan_threshold_replay / corpus_lib / inference_lib） 涉及数据：data/ch10/reports/eval_report.json、golden_report.json、golden_samples.jsonl、corpus_labeled.jsonl

    为什么走到微调这一步¶

    前面意图分类用的是 LLM 结构化输出（第 6 章），好用，但有两个现实问题：

    1. 每句话都调一次大模型，对话量上来后，成本和延迟都吃不消
    2. 意图分类这件事本身是"浅任务"——它不需要深层推理，是个标准的文本分类问题。用大模型做文本分类，杀鸡用牛刀

    所以这章做的是一件事：训一个轻量分类器，替代（或旁路）LLM 做意图/主题分类。目标模型 RoBERTa-wwm-ext，一亿参数级别，CPU 上十几二十分钟就能训完——这是"没有显卡也能跑微调"的起点。

    第一关：语料从哪来¶

    微调要有标注数据。现实是没有现成的运维工单分类语料，所以第一件事是造语料：

    • build_corpus.py + corpus_lib.py：按模板/规则生成各意图的语料（意图 × 说法变体 × 设备/场景填充），全部标记 origin=simulated——数据是模拟生成的，这是底线，评估时心里要有数
    • supplement_sizefit.jsonl：补充尺寸适配样本（让序列长度分布贴近真实输入，避免训练/推理时 padding 浪费）

    造完约 430 条标注语料。规模不大，但足以把 10 类意图的典型说法覆盖住。

    第二关：黄金样例把关，过线才放行¶

    批量预标之前，先立一道质检闸：黄金样例验证。

    golden_samples.jsonl 是 30 条人肉标注、边界最刁钻的样例（预标 prompt 验证，过线 80% 才放行批量预标）。为什么要这道闸？因为批量预标 = 用 prompt 给几千条语料打标签，如果 prompt 本身不行，打出来的标签全是错的，训练就是在喂脏数据。

    实测：30 条命中 25，通过率 83.3%，过线 80% → 放行。

    但看它的失败案例特别有价值——暴露了分类边界在哪：

    输入 期望（gold） 实际（pred） 暴露的边界问题
    电机不转了快来看看 设备报修 故障咨询 "要你修"和"问你咋回事"的边界，光看字面分不清
    电机嗡嗡响还发热,要不要报修 设备报修 故障咨询+设备报修 多标签场景，单标不够
    紧急停机了,多久能来人 设备报修 设备报修+服务承诺 报修里带时效诉求
    报修诊断收不收费 服务承诺 故障咨询 "报修"两个字带偏了意图
    你们卖不卖设备 其他 设备信息 采购意图混进信息查询

    这些失败不是模型笨，是这些句子本来就在类边界上。黄金样例的价值就是把边界问题暴露出来，让 prompt/训练数据针对性补。

    第三关：训练与评估¶

    train.py 全参微调 RoBERTa-wwm-ext，build_dataset.py 做分层划分 + 训练集增强，然后 evaluate.py 逐类算指标。

    实测评估报告（eval_report.json）：

    • 测试集 44 条、10 类，阈值 0.3
    • micro / macro 的 P、R、F1 全是 1.0
    • 每类 support 只有 4-5 条，TP 全命中、FP/FN 全 0
    • 红线：严类（设备报修/工单查询/故障咨询/安全规程）0.9，中类 0.8，全部通过

    但这里必须泼一盆冷水：F1=1.0 在 44 条测试集上不是"完美"，是"测试集太干净"。每类只有 4-5 个样本，全是模板语料变体，模型背都背得过来。真实的分类边界（黄金样例那 5 条）在测试集里根本不在。所以评估体系里红线门槛（严类 0.9）比 F1 数字本身更重要——它是对"这类分错代价大"的保护。

    第四关：部署与旁路¶

    训练完不直接上主链路，因为微调分类器不是用来替代主链路的，是旁路：

    1. export_onnx.py：导出 ONNX 格式（跨平台、部署轻、推理快）
    2. serve.py：推理服务 :8110
    3. classify_pool.py：旁路批量归类——对历史对话池批量打主题标签，不实时介入用户对话

    这章还留了个工具：scan_threshold_replay.py 阈值扫描重放——扫不同置信度阈值下的表现，避免一拍脑袋定阈值。

    这章学到的最重要一课¶

    微调的价值不在"F1 多高"，在"把浅任务从大模型上卸下来"。10 类意图分类这种活，LLM 能做、但每句一次 API 调用，又贵又慢；一个 1 亿参数的小模型 CPU 就能跑，推理毫秒级，还能旁路批量处理历史数据。而 F1=1.0 这种数字，要看测试集规模再下结论——别被漂亮的指标骗了，要看它是在什么数据上算出来的。

    怎么验证¶

    # 黄金样例验证（预标 prompt 把关）
make ch10-golden

# 语料 → 数据集 → 训练 → 评估 → 导出
make ch10-corpus
make ch10-dataset
make ch10-train
make ch10-eval     # 看每类 P/R/F1 + 混淆矩阵
make ch10-export   # 导出 ONNX

# 推理服务 + 旁路归类
make classifier-up
make classify-pool
