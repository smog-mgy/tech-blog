    Agent 学习 11｜全链路验证与复盘¶

    记录日期：2026-08-05 标签：AI Agent · 全链路 · 复盘

    这篇保留学习阶段的概念、示例与验证方法。实际项目实现可沿文末的 OpsDesk 对应章节继续阅读；示例输出不自动视为新一轮实测结果。

    到这里，回头看一眼来时的路：从第 1 章接上第一个 LLM，到 RAG 把知识外挂进来、工具让它够得着数据、架构给它搭了条确定性骨架，再到意图识别、上下文管理、可观测、数据飞轮，上一站还亲手训练出一台分类器。前面一章章走下来，每一块都亲手搭过、接进了系统。所以这一章不再回头拆任何一个零件——前面都讲透了，这里只点名它是谁、回指是哪一章。重心换个视角：把这套已经搭起来的系统当成一个整体，看一条真实请求怎么从头到尾贯穿它、各个零件之间怎么交接协作，再回头把整条路上的选型和踩过的坑一起复个盘。

    一、一条请求的六站接力¶

    一句用户消息从最左边进站，依次经过六站才出站变成回给用户的一句话。这张图第 5 章画过（当时好几站挂着「后面章节细讲」的路牌），现在把整张图重新铺开，每一站挂上它归属的那一章：

    站 干什么 归属章节
    1 指代消解 拿最近几轮把「这个」「它」补全成脱离上下文也读得懂的完整问题，补好的话往后带着走 第 6 章
    2 意图识别 判断用户想干嘛，输出结构化 JSON：intent + confidence。不解决怎么答，只负责送上正确的轨道 第 6 章
    3 按意图分流 骨架最重要的岔口，分流规则写死在代码里 第 5 章
    4 置信度检查 只开在知识线上，卡在检索之后、进 Agent 之前 第 4、5、9 章
    5 主力 Agent 各分支在此汇合收敛，脑子是 ReAct 循环 第 5 章（工具第 2、8 章）
    6 记录日志 想什么、调哪些工具、检索回什么、花多少 token 全留痕 第 9 章

    第 3 站分流的五条轨： - 知识类（政策、商品 FAQ）→ 强制先走一趟 RAG 检索把资料捞出来当上下文（第 3、4 章） - 物流、订单这类业务数据 → 不预先检索，直接送主力 Agent - 退款退货、售后 → 走 refund_flow 确定性子流程：先取订单、再强制检索政策，最后只把「这一单能不能退」交给 Agent 定 - 闲聊和拿不准的「其他」→ 既不检索也不进 Agent，回一句写死的话术 - 投诉 → 先安抚，把「转人工」「建工单」两个选项交用户自己点，不后端自动执行

    第 4 站置信度闸为什么卡在生成之前：检索回来的资料贴不贴问题，分数从检索链路里算（精排分数、命中几条有效证据）；过线放行进 Agent，过不了当场折返走兜底 + 把问题送进数据飞轮。Agent 的答复逐字流式发给用户，等答完再判证据就晚了；这道闸开在生成前还顺手省下一次注定作废的 Agent 调用。证据之外还有一道 useful 自评开在生成阶段（模型边答边判资料撑不撑得起最终回答），两道加上用户反馈没解决，就是第 9 章定的飞轮三个入口。

    贯穿全程的暗线——会话上下文：从第一站起每个节点都往里读、往里写。指代消解翻它才知道「这个」指哪件商品，意图识别读它才判得出用户从物流聊到退款，主力 Agent 的 ReAct 每走一步又塞回新的思考和工具结果。怎么装、装满怎么裁怎么压，是第 7 章的事，落到代码里就是 LangGraph 那份共享的 State。

    二、用 LangGraph 把六站接成一张图¶

    上面这条线在代码里靠第 5 章选定的 LangGraph 连起来——每一站做成图上的一个命名节点，节点用边接起来，State 顺着边走完全程。核心串联就几行：

    graph = StateGraph(ConversationState)
graph.add_node("resolve_reference", resolve_reference_node)    # 指代消解
graph.add_node("classify_intent", classify_intent_node)        # 意图识别
graph.add_node("retrieve_knowledge", retrieve_knowledge_node)  # 知识类走 RAG
graph.add_node("confidence_check", confidence_check_node)      # 置信度检查
graph.add_node("main_agent", main_agent_node)                  # 主力 Agent 收敛

graph.add_conditional_edges("classify_intent", route_by_intent, {
    "knowledge": "retrieve_knowledge",   # 知识类走检索
    "refund_flow": "fetch_order",        # 退款退货 / 售后进子流程
    "business": "main_agent",            # 物流、订单直接进 Agent
    "fallback_script": "fallback_node",  # 闲聊、其他走固定话术
    "escalate": "escalate_node",         # 投诉：安抚 + 交用户选
})
graph.add_edge("retrieve_knowledge", "confidence_check")       # 检索完先过证据闸
graph.add_conditional_edges("confidence_check", confidence_gate, {
    "strong": "main_agent",              # 证据够，放行进 Agent
    "weak": "fallback_node",             # 证据弱，兜底 + 记入问题池
})

    三、走一条完整请求：「早上买的蓝牙耳机还能退吗」¶

    假设用户前一句刚问过蓝牙耳机的到货时间，这一句甩过来：「我早上买的这个还能退吗」。

    1. 指代消解：拿最近两轮一看，「这个」指刚聊过的蓝牙耳机，补全成「我早上买的蓝牙耳机还能申请退货吗」，写进 State
    2. 意图识别：判成退款退货类、把握也高，产出 {"intent": "退款退货", "confidence": 0.9}，塞进行李箱
    3. 分流：判成退款退货，走 refund_flow 那条边，进确定性子流程
    4. 子流程（写死的步子）：
    5. 第一步查订单（确定性节点）：拿补全里的线索查这单——三小时前下的、还没发货；万一没传订单号，就弹订单选择器让用户点选回填（第 6 章）
    6. 第二步取政策：写死一趟强制检索，把退款政策捞出来当依据；借上刚拿到的订单状态做 Query 扩写，比光凭一句「能不能退」扩得准（第 4 章）
    7. 主力 Agent：拿着「三小时前下单、还没发货」对上「未发货可全额退」这条政策，判定能退，组织出「这笔订单还没发货，支持全额退款，是否帮您提交」——订单和政策都齐了，Agent 只做这最后一步判断
    8. 置信度闸开在知识线上，这趟子流程的车不停那一站；useful 自评有订单数据和明确规则撑着判为真，正常回复
    9. 记录日志：查了哪笔订单、强制检索捞回哪条政策、Agent 怎么判断、花了多少 token，每一步都记进调用树

    四、再走一条兜底进飞轮的请求：「跨店满减能叠会员积分券吗」¶

    翻车本身也是流程的一部分：

    1. 前两站照常：指代消解没什么可补，意图判成商品咨询（知识类）
    2. 分流：知识类触发强制走 RAG 的硬规矩。可这条跨店满减叠加规则是刚出的活动细则，知识库还没来得及补——检索回来几条都沾边、又都答不到点子上
    3. 置信度检查：证据都不贴问题，证据置信度过不了线，当场折返——主力 Agent 压根没出场，也就没有机会硬凑一个像那么回事的答案
    4. 兜底：老实回「这个活动细则我还没查到准信，请您转人工确认」，同时把「跨店满减能否叠加会员积分券」送进低置信度问题池
    5. 飞轮接住：标准化去噪成 FAQ 式标准问法 → 查重（有人问过就累加频次）→ 待审队列等人补答案 → 写回知识库。下次再有人问，检索直接命中就答得上。问题还会被第 10 章那台分类器按主题批量归堆，看哪类最缺知识、先补哪块

    五、踩过的坑：一张收拢各章教训的清单¶

    坑 现象 解法 章节
    关键词查表必漏召回 「邮费是多少」对不上库里「运费怎么算」 上 RAG 换语义检索 第 2→3 章
    向量单路也有短板 SKU、型号、优惠券代码这类靠字面对齐的词漏 补 BM25 关键词路、RRF 融合再 Rerank 精排 第 3→4 章
    切分切歪一寸 退货条款被从中间切开，检索只命中前半句就敢答「可以退」 结构感知切分 + 关键条款标记 第 3 章
    扩召回别在入库侧做 一条知识拆多个问法占满 Top-K、挤掉更相关的 检索侧 Query 扩写，库每条知识只存一份 第 4 章
    Agent 有时守不住硬约束 跳过 RAG 凭记忆乱答、该拒答时乱编 Workflow 骨架把强制检索/强制取证/投诉转人工写死在流程里 第 5 章
    意图边界定义不清 准确率上不去，再大的模型也判不稳 prompt 里每类意图边界划清楚（和模型能力并重的第一杠杆） 第 6 章
    光靠滑窗漏早期上下文 聊回二十轮前的订单就丢 分层：近处原文、中间截短、最远压摘要，额度从窗口倒推 第 1→7 章
    数据质量决定微调成败 「买大了想退」有的标两类、有的标一类，模型学歪 数据质量排在模型大小和训练技巧前面 第 10 章

    规律贯穿整个系统：越是出在数据和流程上的坑，越致命——模型再强，也补不回切分得不对的一刀、标乱的一个标签，更救不回出现幻觉时的流程。

    六、技术选型指南：什么场景该选什么¶

    凡是涉及准确率、召回率、延迟这类数字，都要等开发后拿自己的评估集实测，这里只给定性理由：

    环节 选什么 为什么 / 什么场景才真用得上
    接 LLM 写 Prompt LangChain ChatOpenAI/PromptTemplate/结构化输出原语都封装好；多模型切换收进 .env 代码不动（第 1 章）
    编排整条流程 LangGraph 要分流、要汇合、还得循环、状态一路贯穿，链式拼不出来才需要图模型；主力 Agent 也只是其中一个节点（第 5 章）
    嵌入模型 BGE-M3（或 Qwen3-Embedding） 私有化、数据不出境、想领域微调、中英都要——闭源 API 直接筛掉；学习演示用云端即可；具体选哪个拿自己评估集实测（第 3 章）
    向量库检索 Milvus 一库扛两条路 扛得住大规模 dense，2.5 起内置 BM25、原生 RRF 融合；搞 demo 嫌重可先用 ChromaDB 轻量起步（第 3、4 章）
    精排 bge-reranker 类 Cross-Encoder 召回负责找得全、精排负责排得准；准但慢，只在召回缩到 Top-50 的小候选集上跑（第 4 章）
    意图识别 LLM + prompt 复杂多轮客服本质是对话状态追踪，得读懂整段脉络，单句小模型处理不了；边界清晰、单句分类的场景才轮到规则或微调小模型（第 6 章）
    会话上下文 LangGraph State 上下文随图一路流转，每个节点读写同一份（第 7 章）
    工具生态 内置 @tool + 外部 MCP 内置够跑课程；要接一堆外部系统、新工具注册即用，就得靠 MCP 标准协议（第 8 章）
    可观测 Langfuse（或 LangSmith） 开源自部署、数据留墙内，环境变量 + 编译时挂一次回调零侵入还原调用树；不介意上云可换同源的 LangSmith（第 9 章）
    微调 RoBERTa-wwm-ext 全参微调 分类首选编码器、省几个量级，这个体量几个 G 显存就够，LoRA/QLoRA 是大模型才用得上的（第 10 章）

    七、本章小结¶

    回头看这条从第 1 章铺到现在的地铁线：从接上第一个 LLM 起步，一路把 RAG、工具、架构、意图、上下文、可观测、飞轮、微调一样样搭了起来，全程用 Claude Code + Superpowers 的纪律零手写代码交付。走完这一趟，手里攥着的不只是一堆知识点，是一个能上线跑通、能写进简历、能扛住面试追问、覆盖当下最高频考点的完整 AI Agent 项目。

    链路真跑通过，弹药已经装满。剩下的，就是把它认认真真做一遍，然后走进面试间，把这条亲手跑通的线，自信地讲出来。
