    学习笔记 03｜RAG 基础：跑通「先查资料再回答」全链路¶

    日期：2026-06-18 标签：AI Agent · RAG · 知识库

    上一章收尾翻车现场还历历在目：faq 表里明明躺着「运费怎么算 → 单笔订单满 99 元包邮……」，用户一句「邮费是多少」却查了个空。病根不是数据，是查法——LIKE 认字面，用户嘴里的「邮费」在「运费怎么算」里字面上根本不存在。这一章把 query_faq 的查法整个换掉，让它能听懂「邮费」和「运费」说的是同一件事。这就是 RAG。

    一、核心思想：把「意思」变成机器能算的东西¶

    字面对得上纯属运气¶

    给「运费」配同义词表（邮费、快递费），给「包邮」挂上（免运费、满多少免邮）——补是能补，可用户说法无穷无尽：手滑错别字、口语化、换个行业黑话……补到最后你维护的是一本《电商黑话大辞典》，永远补不完。

    真正该换的是查找方式本身。人理解「邮费是多少」靠的是字背后的意思；要让机器也做到，得先把「意思」这个抽象概念变成机器能算的东西——一串数字，也就是向量。意思相近的内容，数字上也挨得近。围着这个思路搭起来的整套查、答机制，就是 RAG（Retrieval-Augmented Generation，检索增强生成）。

    RAG 解决什么问题¶

    模型的知识全部固化在训练那一刻的参数里，之后再也不更新： - 上周刚改的退货政策，它不知道 - 新出的蓝牙耳机参数，它没学过 - 碰到不知道的，它不会老实说「不知道」，而是天性般把「下一个最像话的词」接着编下去——编得越流畅，错得越理直气壮

    RAG 的思路：给模型一个外挂的库，每次回答问题先现查，查到什么照着什么答，库里没有就老实说没有。 库里的内容随时能更新——退货政策改了，换一份文档就行，不用重新训练模型。名字拆开看就是三步：Retrieval（去库里捞相关片段）→ Augmented（拼进模型这次要看的材料）→ Generation（照材料组织回答）。

    模型本身没变聪明一分——这些问题的重点不是智商，是数据。

    知识库里该放什么¶

    第一反应可能是存历史客服对话——这个想法要纠正。原始对话东一句西一句，夹着寒暄废话，噪声太大，不适合直接检索。

    真正该放的是权威、结构清楚的文档：

    类别 例子
    退款退货政策 7 天无理由规则、例外条款
    商品 FAQ 规格、功能、使用方法
    售后服务手册 保修条件、换货流程
    支付与发票 FAQ 开票、退款到账
    促销活动规则 满减、优惠券使用
    账号安全/评价规则 封号、评价修改

    共同点：内容相对稳定，但会更新——这正是 RAG 的用武之地。

    二、知识从哪来：写文档的人 + 聊过天的人¶

    来源 1：人工整理¶

    懂业务的人把政策写成结构化 Markdown（一级标题、二级标题、正文段落层次分明）。这么写有讲究：结构感知切分吃这套结构红利。原则一句话：每一块内容都要能独立说清一件事，不能东一句西一句掺在一起——垃圾进，垃圾出。

    来源 2：历史客服对话挖掘（重点）¶

    聊天记录里全是真实用户会问的问题，是一座金矿，但挖出来的是原始矿石。做法：拿一批会话喂给 LLM，让它抽取「用户问了什么、客服怎么答的」问答对，写进暂存表，等所有批次抽完，整体去重，才是能入库的问答对。

    例：用户「上次买的连衣裙偏大，想换小一码」/ 客服「可以，签收后 7 天内都能申请换货，运费我们出」→ 抽成「买的衣服尺码不合适能不能换货」/「支持签收后 7 天内换货，运费商家承担」。寒暄、口语、上下文依赖全被摘掉。

    为什么要分批喂，不能一股脑全塞？ 1. 上下文有硬性 token 上限，塞不进去 2. 数据一多，抽取质量反而掉——两个机制： - 幻觉变多：材料又长又杂，模型分心，把不同会话串味，硬凑出没出现过的问答对（「上下文焦虑」） - 准确率下降：「Lost in the Middle」现象——开头结尾模型看得认真，中间部分一带而过

    一批只放几十个会话，读得过来也不容易串味。

    三、两条流水线：离线建库 + 在线问答¶

    离线建库 在线问答
    干什么 解析 → 切分 → 向量化 → 存库 问题向量化 → 查库 → 交给模型生成回答
    时机 提前跑，定期更新，用户无感知 用户每问一句走一遍
    被谁盯着 没人 用户的等待

    两条线各干各的，接口只有一个：向量库。离线建好的库就是在线要查的库，库建得好不好直接决定查不查得着。

    本章按两条线顺序走：先离线（文档解析→切分→Embedding→向量库→双写），再在线（只跑通 dense 向量单路检索）。

    四、文档解析：读错一个字，后面全白搭¶

    坑 情况 处理
    无边框表格（最要命） SKU 价格表靠空格对齐撑行列，解析器认不出，价格错配到下一行型号，用户拿错报价下单 强表格识别能力，普通文本抽取顶不住
    多栏排版 政策文档多是单栏+目录 按顺序读基本不乱
    印章遮挡/扫描模糊 资质证明、盖章合同；章压字、分辨率低发虚 重型通道：印章层与文字层分离，文字层 OCR，模糊先增强再识别

    工程上不能一刀切都上最贵最慢的解析：先加一层分类判断，判定为「难啃」的才送重型通道，其余走轻量通道，速度和准确率兼顾。

    顺手做一件小事：建电商领域术语词库（SKU、满减、花呗分期、运费险），清洗和切分识别结构时垫底。

    五、切分是隐形地基：切歪一寸，模型就敢乱答¶

    反例：退货政策「支持 7 天无理由退货，商品需保持完好，以下情况除外：定制商品、已拆封的个人护理类商品、赠品需与商品一并退回」。固定长度切分正好切在「以下情况除外」后面 → 前半块单独成块「支持 7 天无理由退货，商品需保持完好」。用户问「定制款杯子能退吗」，命中前半块，模型读不出例外，大大方方答「可以退」——定制明明不退。不能怪模型，是切分先把信息切没了。

    三代演进（每一代都是被上一代的毛病逼出来的）¶

    第一代：固定长度切（每 500 字一刀） - 优点：一行代码 - 毛病：完全不管内容，句子被拦腰砍断，上面的例子就是这么翻车的

    第二代：按句子边界切 + 块间重叠 - 解决：句子不砍断、关键信息不卡边界 - 遗留：没有章节层级关系。用户要定位「退货政策」里「无理由退货」怎么规定的，模型拿到块却不知道它挂在哪一节底下，按章节定位、溯源接不住

    第三代：结构感知切分（Markdown 标题层级） - 一级二级标题各自成层，每块语义独立完整 + 带 section_path 层级路径：

    {
  "answer": "支持 7 天无理由退货，商品需保持完好，以下情况除外：定制商品、已拆封的个人护理类商品、赠品需与商品一并退回。",
  "section_path": "退货政策 > 无理由退货"
}

    这一块知道自己是「退货政策 > 无理由退货」节，按章节定位、答案标引用溯源全靠它。这就是为什么人工整理要按标题分层——结构感知切分吃的正是这份结构。

    切分细节¶

    • 超长章节分级让：先按小节切 → 小节还长按段落 → 段落还长才落到句子，优先保住更大的语义单元
    • 重叠裁到最近句号：别固定截一段字数把半截话带过去——半句进来不补信息还添噪音
    • 大表格按行切要复制表头：每块都带一份表头，否则模型拿到的是「中间几行数字」，分不清哪列是尺码哪列是价格
    • 碰上无标题层级的长文本：语义切分（按相邻句子向量相似度找断点）更合适；或切好后先补一段交代位置和角色的上下文再向量化

    六、Embedding 选型：数据合规放最前¶

    企业硬门槛¶

    1. 私有化部署：电商客服是企业级场景，数据不能外泄
    2. 能微调：拿自家语料微调
    3. 中英文都顶得住

    这三条一出，闭源商用 API（OpenAI text-embedding、Voyage、Cohere）直接出局——不管效果多好，数据出不去、进不了私有环境、没法微调。学习/课程演示用云端即可，避免本地部署太重。

    开源候选对比¶

    模型 特点 结论
    BGE-M3 100+ 语言、8192 token 长文本、中英文稳、可微调、生产用得多、踩坑资料多 本项目默认选
    Qwen3-Embedding 同路线，多语言更强，主打 4B/8B 大档，有 0.6B 轻量档 随时能换
    gte-multilingual-base Apache 2.0 商用无碍、小巧跑得快、能力够用 没有非它不可的亮点，往后排
    jina-embeddings-v3 权重 CC BY-NC 非商用协议 商用要另谈授权，放备选

    选型逻辑拆解¶

    • 参数大 ≠ 检索效果好：瓶颈很少卡在 Embedding 参数规模，更多卡在切分质量、是否单路检索、有没有重排、要不要领域微调。电商场景用户问题短、知识范围有限（自家商品+自家政策），不是开放域百科，轻量档（0.6B）足够
    • 维度 vs 成本：BGE-M3 固定 1024 维。想砍维度换 MRL 训练过的模型（重要信息压在靠前维度，截短精度损失不大），Qwen3-Embedding 和 OpenAI text-embedding-3 都支持按需设维
    • query 指令：有的模型给 query 端单独加检索指令/前缀（E5 的 query:、Qwen3 的 query 指令）能抬效果；BGE-M3 默认不用加，query/document 一视同仁
    • 优先级排序：数据合规 → 中英文表现/可微调 → 向量维度存储成本 → 自部署算力

    七、向量库选型¶

    方案 定位 说明
    FAISS 纯检索库，无服务层 只存向量+数字 ID，不存原文、无字段过滤，demo 级
    ChromaDB 嵌入式，开箱即用 开发期省心，撑不住生产并发
    pgvector PostgreSQL 插件 复用现成库，SQL 过滤/事务天生就有，中小规模
    Milvus 专业分布式向量库 索引丰富、原生标量过滤、扛大规模高并发；2.5 起自带 BM25 全文检索，dense+BM25 同库共存，方便混合检索
    Qdrant 同上 备选

    本项目选 Milvus：向量规模持续涨 + 按品类/店铺过滤的标量查询少不了；个人开发嫌重可用 ChromaDB 先跑。

    ANN：近似最近邻¶

    「近似」= 不保证绝对最相似，拿一点精度换数量级速度。几十万条向量逐条比对，一次查询能等哭用户。

    • HNSW：多层图，从稀疏顶层入口往下钻、顺着邻居走到最相似点附近。查得快召回高，代价是建图占内存、写入慢 → 读多写少场景
    • IVF：先聚簇，查询只在最近几个簇里精算，跳过其余。建库快省内存，召回随「查几个簇」参数走 → 规模越大越划算

    八、向量库和业务库，为什么要分家¶

    1. 向量是原文的派生品，计算有损——不能拿一串数字反推原文；但随时能重算（原文没变，重跑 Embedding 一模一样）。后面微调 Embedding、调整切分、换维度都要全量重生成向量，原文留在 MySQL 就是重跑一遍脚本的事
    2. 职责各司其职：向量库专精相似度查找；业务上要事务、SQL 过滤、被多个服务共读的原文本该放关系型库

    四种落地方案（从轻到重）¶

    1. FAISS + sidecar（pickle/SQLite 存原文，零额外服务）
    2. FAISS + MySQL（vectorId 关联，业务字段多了升级划算）
    3. Milvus/Qdrant 一体（原文和元数据进向量库自带存储，少运维一套，多一套分布式系统）
    4. 本项目：Milvus 存正文+检索元数据（同份正文还能开原生 BM25），MySQL 当权威事实源（会话、工单、待审数据），靠 vectorId 关联。检索时直接从 Milvus 取正文元数据，要补全业务上下文再拿主键回 MySQL 捞

    九、双写落库：一个状态位换来的可重跑¶

    知识块从切好到能被检索，走一趟双写：

    1. 切好的块先写 MySQL，状态 待向量化，vectorId 留空
    2. 调用 Embedding 算向量，连同正文、检索元数据写进 Milvus，拿到 Milvus 分配的 ID
    3. 回写：vectorId 补回 MySQL 记录，状态转 已向量化

    一个布尔状态位，换来：随时扫 MySQL 揪出卡在「待向量化」的记录（=上次向量化中断的残骸），直接重跑这批，不用整库推倒。按 chunk 主键幂等 upsert，重复写不产生两份。

    当前同步走（切完一块立刻跑完四步）；数据量大了换异步队列：先全落 MySQL 标 pending，后台顺着 pending 建向量，建完一条改一条。

    十、一条 chunk 长什么样¶

    先澄清易混点：这坨 JSON 不会整个拿去向量化。真正送进 Embedding 的只有 category、questions、answer 三格拼起来的文本，其余是给检索过滤和溯源的元数据，不进向量。

    两类内容的差别：questions 从哪来¶

    ① 带真实问题的（商品 FAQ、对话挖出来的问答对）

    {
  "category": "退换货",
  "questions": ["买的鞋子能不能退", "七天无理由适用哪些商品"],
  "answer": "支持 7 天无理由退货，商品需保持完好，定制类商品除外。",
  "section_path": "退货政策 > 无理由退货",
  "content_type": "text",
  "is_key_clause": true,
  "prev_chunk_id": "kb_00417",
  "next_chunk_id": "kb_00419"
}

    ② 纯文档（政策、售后手册）——没有天然问题，questions 填所在章节标题，category 填上级标题路径：

    {
  "category": "退货政策-无理由退货",
  "questions": ["例外情况"],
  "answer": "以下情况不支持无理由退货：定制商品、已拆封的个人护理类商品、赠品需与商品一并退回。",
  "section_path": "退货政策 > 无理由退货 > 例外情况",
  "content_type": "text",
  "is_key_clause": true,
  "prev_chunk_id": "kb_00418",
  "next_chunk_id": "kb_00420"
}

    元数据四类（都不进向量）¶

    字段 作用
    section_path 章节路径，答案溯源定位靠它（贯穿全流程的暗线：切分时存进去，检索带着走，生成答案做引用溯源映射回原文）
    content_type 文字/表格/图片
    is_key_clause 是否退货售后这类关键条款，检索排序加权信号——接上切分反例：关键条款入库前就必须保证完整成块
    prev_chunk_id / next_chunk_id 相邻块指针，语义不完整时自动拉前后块补全

    十一、在线问答：先跑通向量单路¶

    from langchain_huggingface import HuggingFaceEmbeddings
from langchain_milvus import Milvus

embeddings = HuggingFaceEmbeddings(model_name="BAAI/bge-m3")
vector_store = Milvus(
    embedding_function=embeddings,
    connection_args={"uri": "http://localhost:19530"},
    collection_name="ecommerce_kb",
)
retriever = vector_store.as_retriever(search_kwargs={"k": 10})

docs = retriever.invoke("邮费是多少")

    LangChain 三件套：HuggingFaceEmbeddings（文字→向量）、Milvus（存和查）、as_retriever（包成「问题→文档」的统一接口）。retriever.invoke 一次调用内部就是：编码问题 → Milvus 查相似度 → 吐出命中的 chunk 连同元数据。

    query_faq 换内脏不换签名：函数体换成 await retrieval.search_knowledge(keyword)，参数还是那一个 keyword，@tool 装饰器不动——调用方不知道底下换过，system prompt 不用改，模型看到的 schema 一个字节没变。这就是工具模块化的红利。

    回到那句「邮费是多少」：「邮费」和「运费」在向量空间里挨得近，稳稳命中。同义词词典正式退休。

    十二、代码走读要点¶

    开工前冒烟：验维度¶

    resp = await client.embeddings.create(model=settings.embed_model, input=["邮费是多少", "运费怎么算"])
assert dims and dims[0] == 1024, f"期望维度 1024,实际 {dims}"

    维度会被写死进 Milvus 集合 schema，集合建好就改不了字段维度，得删了重建。先验 1024 比灌一半数据才发现划算得多。

    嵌入客户端：单例挡连接泄漏¶

    进程内单例复用同一 httpx 连接池——每次 embed 新建 AsyncOpenAI，建库那种成百上千次调用会一路累积连接和 fd 撑爆。两个口子：embed_texts（批量建库）、embed_query（单条在线），后者直接套前者。嵌入上游和聊天上游是 .env 里分开的两组配置，选型完全不相干。

    切分原语细节¶

    • 中文分隔符表要自己写：LangChain 默认表给英文准备（靠空格找词边界），中文没有词边界。自排版在换行后插句末标点层（。！？；），再逗号空格，最后才逐字——切下来至少落在句子/分句边界
    • strip_headers=True：标题从正文摘掉但留在 metadata，装配时拼 section_path、questions、category
    • 句末重叠：recursive_split 自带 chunk_overlap 按字符数取，接过来多半是半截话；自写的 apply_sentence_overlap 从块尾倒着凑完整句，if out and 保证第一句无论多长都收进来（宁可重叠超一点，不给下一块接半截）
    • 表格识别：判据「这行以竖线开头且下一行是分隔行」，允许表前有散文导语；每块重贴表头+分隔行（preamble 只跟首块走）；行数少的整块返回
    • is_key_clause：只扫标题+正文前 40 字——关键词在开头才说明这块讲的就是这件事；整块搜会把顺带提一句「运费另计」的商品介绍也标成关键条款
    • sources.py 一处维护：文档清单被离线 CLI、切块预览、浏览器录入页三处共用，各写一份会账对不上

    双写幂等的支点¶

    • Milvus 集合 auto_id=False：主键直接用 MySQL 的 id，两库共享同一身份，天然幂等 upsert
    • 向量化文本 = category\nquestions\nanswer 三格
    • write_pending 两趟循环：先插入拿自增 id，再回头连 prev/next（邻居 id 那时才存在）
    • 建库 CLI 直接 INSERT 无天然幂等 → 先 count 挡住重跑，想重建 make kb-reset

    挖知识的坑¶

    • 并列数组规避 502：按直觉该写 list[QaPair]（问题对象数组），实测上游对嵌套对象数组的工具 schema 直接 502，换两个并列标量数组 questions: list[str] + answers: list[str] 正常——代价是没人替你保证对齐，长度不一致按较短截断+记警告（少抽两条没事，问题错配到别人的答案会污染知识库且很难查）
    • 去重归一化：[\s\W_]+ 去空白标点——注意 \W 不含中文（中文属 \w），不会把汉字吃掉；「运费怎么算？」和「运费怎么算」归一成同一键；seen 初始装库内存量，一趟同时挡本批撞车和存量撞车
    • 暂存表 + 人工审核：挖出来的问答对不直接入库——客服当时的回答可能只对那一单成立、带着订单号或「稍等我看看」这种废话，进库后每次检索都可能捞出来当依据。先落 staging 标 extracted → 去重标 kept/discarded → 入库口只有一个：/staging/approve 人工逐条采纳，只认 kept 状态（手快点两下被 409 挡回）。采纳的块 content_type 标 mined，跟人写的块能区分——后面几章都用这个区分
    • batch_no 过滤是踩坑后加的：挖到一半崩了会留一批 extracted 残骸，不圈定批次会把残骸卷进下次去重

    十三、实战验收¶

    验收标准： 1. 「邮费是多少」这类换说法的问题，能召回运费说明并答对（浏览器里气泡出现工具徽章 + 正确运费规则） 2. 故意中断建库任务再重跑，漏向量化的块能被捡起补齐（vectorize_status=pending 兜底）

    演示链路：make kb-build（解析切分+双写）→ make kb-vectorize（向量化，可重跑）→ 浏览器问「邮费是多少」→ 命中运费知识块。

    十四、本章小结¶

    • 思想：意思相近 = 向量挨得近；RAG = 外挂知识库，先查再答，库可随时更新，不用重训模型
    • 知识：放权威结构文档；来源 = 人工整理 + 对话挖掘（分批喂防上下文焦虑/Lost in the Middle，暂存表人工审核入库）
    • 切分：三代演进到结构感知，section_path 贯穿全流程；重叠裁句号、表格复制表头
    • 选型：Embedding 合规优先选 BGE-M3；向量库选 Milvus（HNSW/IVF 按规模取舍）
    • 分家：MySQL 权威源 + Milvus 向量检索，vectorId 关联，双写+状态位保幂等可重跑
    • 换内脏不换签名：query_faq 从 LIKE 变成向量检索，对外契约不变

    留下的坑：用户报一串 SKU 编号或具体型号，这类查询看重字面对得上；向量检索认语义相近，反而容易晃到几个长得像但答非所问的结果。这个缺口，第 4 章混合检索来补。
